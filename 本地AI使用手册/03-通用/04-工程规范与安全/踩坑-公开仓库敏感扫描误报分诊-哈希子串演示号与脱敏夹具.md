# 问题：公开仓库敏感扫描的误报分诊：哈希子串、演示号与脱敏夹具

## 一句话结论

对已公开仓库跑手机号/邮箱/私钥/密钥正则扫描，命中不等于泄露：SHA-256 十六进制串内部会命中手机号正则、`13800138000` 是演示号、脱敏拒绝测试的「坏输入夹具」只含 `-----BEGIN PRIVATE KEY-----` 一行。每条命中必须看上下文分诊，否则会把干净仓库报成泄露、或把真泄露淹没在误报里。

## 触发条件与影响

- 项目或功能：仓库转公开后的暴露面审计（本机 CodeWeave 于 11-06 公开到 GitHub/GitCode）。
- 环境与版本：`git ls-files` + `git show HEAD:<path>` 逐文件扫描（只扫已跟踪内容，不扫工作区私有数据）。
- 触发条件：用裸正则 `1[3-9]\d{9}`、邮箱、`BEGIN … PRIVATE KEY`、`(api_key|secret|token)=…` 扫全仓。
- 影响范围：安全结论的可信度;误报会触发不必要的「清历史/改号」动作。

## 复现步骤

1. 前置条件：仓库含 SHA-256 证据文件、演示账户夹具、脱敏拒绝测试。
2. 操作：对已跟踪文件跑上述正则。
3. 预期：命中即疑似泄露。
4. 实际：手机号 15 处、邮箱 122 处、私钥 2 处、secret 2 处，**分诊后全部为误报或夹具**。

## 证据

- 手机号：`13058931383`(5 处) 与 `15976250116`(1 处) 均出现在 SHA-256 串内部（如 `…D13058931383EEA6238765949829C355CA8`）；`13800138000`(9 处) 为经典演示号。
- 邮箱域分布：`example.test` 84 / `b.com` 24 / `example.com` 10 / `email.com` 2 / `qq.con` 2，**无真实域**。
- 私钥：`native_tests.cpp:1179` 把 `"-----BEGIN PRIVATE KEY-----"` 与 `"Cookie: demo"`、`postgres://user:demo@localhost/db` 一起喂给 `assert(!save(bad).ok)`——是**脱敏拒绝断言的坏输入**，只有 BEGIN 行、无密钥体。
- secret：测试口令 `super-secret-passphrase` 等，非真实凭据。
- 凭据类文件（.jks/.keystore/.pfx/.pem/.key/.env/key.properties）入库 0；`工作区/` 仅 2 个白名单文件入库。

## 根因分析

- 已确认的根因：正则只看字符形态不看语义上下文;十六进制哈希与手机号数字空间重叠;安全测试必然包含「坏样本」。
- 排除过的假设：曾怀疑真实手机号/真实私钥入库，逐条看上下文后排除。
- 问题归属：审计方法（修改前已存在的认知陷阱）。

## 最小修复

扫描后加**分诊步**：① 手机号命中先检查是否落在 `[0-9a-f]{32,}` 哈希串内；② 比对演示号名单（13800138000 等）；③ 私钥/secret 命中看是否位于「断言拒绝」的测试输入列表；④ 邮箱看域是否为夹具域。只有分诊后仍成立的命中才报泄露。

## 验证记录

- [x] 格式化或静态检查：15+122+2+2 命中逐条分诊完毕。
- [x] 类型检查或编译：不适用。
- [x] 单元、集成或端到端测试：脱敏夹具处确认其所在断言为 `assert(!save(bad).ok)`。
- [x] 构建：不适用。
- [x] 启动或手动回归：`git ls-files` 凭据类 0、工作区白名单 2，复核一致。

## 可复用规则

公开仓库暴露面审计 = 正则扫描 + 上下文分诊 + 入库清单核对，三步缺一不可。只扫已跟踪文件（`git show HEAD:`），不扫未跟踪私有数据；结论写「分诊后干净/发现 N 处真泄露」，不写裸命中数。适用：任何转公开或对外交付前的仓库。例外：若命中确为真凭据，立即按泄露处置（轮换+清历史），不走分诊豁免。

## 适用范围与不适用范围

- 适用：公开/交付前暴露面审计、审查他人仓库的安全声称。
- 不适用：运行时内存/日志中的凭据泄露（需另查）。

## 剩余风险

历史提交（非 HEAD）中的泄露不在 `git show HEAD:` 扫描范围；转公开前若曾提交过真凭据，需另扫全历史。本仓库已做过 email 清洗，但清洗范围是否覆盖凭据未验证。
