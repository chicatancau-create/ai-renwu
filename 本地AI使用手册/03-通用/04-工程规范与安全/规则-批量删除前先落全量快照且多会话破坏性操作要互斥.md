# 规则：批量删除前先落快照；多会话共用工作区时破坏性操作要互斥

## 一句话结论

2026-11-26 `G:\AIrenwu` 发生一次**真删且不可恢复**的事故：另一个并行 AI 会话在清理「git 污染」时删掉了 8 个真实工作对象（约 62.6 MB / 183 条目）。事后四条恢复路径**全部走空**——回收站没有、git 无历史、全盘无备份包、VSS 需提权未查成。唯一能定损的，是我在删除前 90 分钟拍的 `all.csv` 全量快照。**这条快照是本次事故唯一证据来源**，因此规则化。

## 触发条件与影响

- 项目或功能：`G:\AIrenwu` 工作区治理（`.gitignore` 用 `/*` 白名单，绝大多数真实目录处于未跟踪态）
- 环境与版本：Windows 10/11 + PowerShell 7 + Python 3.12
- 触发条件：① 任何「按清单批量删除」；② 同一工作区同时有 ≥2 个 AI 会话在写
- 影响范围：不可恢复的数据丢失；本次丢失 6 个实物对象（另 2 项为临时件与垃圾，删得对）

## 复现步骤（即事故经过）

1. 前置条件：一个多会话共用的工作区，`.gitignore` 白名单使大量真实目录未被 git 跟踪
2. 操作或命令：并行会话用「磁盘顶层 minus git 跟踪树」判定污染并批量 `Remove-Item`
3. 预期结果：只删被错误跟踪的外来文件
4. 实际结果：8 个顶层对象被删，其中 6 个是真实工作产物

## 根因分析

- 已确认的根因：
  1. 判定方法错——用「磁盘 minus 跟踪树」当污染定义，在 `/*` 白名单工作区里等价于「删掉所有未跟踪目录」。
  2. 无删除前快照——并行会话没拍，我也只是在做自己的任务时顺手拍了，纯属侥幸。
  3. 无会话互斥——同一个工作区同时跑 4 个 AI 会话，彼此不知道对方在做什么。
- 排除过的假设：
  - 「能找到回收站副本」——否，186/156 条目全扫 0 命中。
  - 「git 历史里能捞回来」——否，白名单下这些路径从未被跟踪。
- 问题归属：环境或依赖（多会话共用）+ 判定规则缺陷

## 最小修复

1. **删除前快照**（本次实际用的脚本，`snap_before.py` 思路）：

```python
import csv, hashlib, os
ROOT = r"G:\AIrenwu"
SKIP = {".git"}
rows = []
for dp, dn, fn in os.walk(ROOT):
    dn[:] = [d for d in dn if d not in SKIP]
    for name in dn + fn:
        p = os.path.join(dp, name)
        try:
            st = os.stat(p)
        except OSError:
            continue
        h = ""
        if os.path.isfile(p):
            hh = hashlib.sha256()
            with open(p, "rb") as f:
                for chunk in iter(lambda: f.read(1 << 20), b""):
                    hh.update(chunk)
            h = hh.hexdigest()
        rows.append([os.path.relpath(p, ROOT), st.st_size,
                     int(st.st_mtime), h])
with open("before.tsv", "w", encoding="utf-8-sig", newline="") as f:
    w = csv.writer(f, delimiter="\t")
    w.writerow(["相对路径", "字节", "mtime", "SHA256"])
    w.writerows(rows)
```

2. **删除前冻结全量备份**到另一块盘（本次 `H:\AIrenwu-备份\20261126_整理前\`，robocopy `/E /COPY:DAT /R:1 /W:1 /XJ`，17012 文件 / 965.11 MB）。
   `/XJ` 不能省——工作区里有 Junction 指向活体 `node_modules`。
3. **破坏性操作加互斥**：在工作区根放 `.lock`（写明会话 ID、开始时间、操作范围），结束才删；后到的会话看到 `.lock` 就先停。
4. **污染判定只用 diff additions**：`git diff --name-only <远端正确SHA>..<本地污染SHA>` 的 additions 才是污染；untracked/ignored 一律不动。

## 可复用规则

1. **要删东西之前，先拍全量 CSV 快照（路径 + 字节 + mtime + SHA256），落进任务夹 `02_证据日志`**。别放 TEMP——TEMP 会被 Windows 更新重启清空（见 [[踩坑-回退备份与取证放TEMP会被更新重启清空且日志会滚存]]）。
2. **删除前必须先冻结一份全量备份**到另一块物理盘，并记录文件数 / 体积 / 退出码。
3. **多会话共用工作区**：破坏性操作前放 `.lock`，操作范围写清楚；不确定别人的会话在干什么就先问、或等它空闲（判据：`C:\Users\Admin\.dsh\sessions\--<项目>--\` 下 `session-*` 文件不再增长）。
4. **污染定义只能用「被错误跟踪」判定**，即 `git diff --name-only` 的 additions；**untracked 目录一律不动**。
5. **验收要能回答「删了多少、删了什么、能不能恢复」三问**。答不出就别动手。

## 适用范围与不适用范围

- 适用：任何「白名单 `.gitignore` + 多会话 + AI 自动执行」的工作区（本机 `G:\AIrenwu`、`D:\Skills`、`E:\fullstack-code` 都属此类）
- 不适用：单会话独占、且删除对象完全由 git 跟踪的仓库（这类 `git checkout` 就能回滚）
