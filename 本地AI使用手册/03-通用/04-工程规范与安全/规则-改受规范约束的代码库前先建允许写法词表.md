# 结论：先建允许写法词表，再动手改；改完用差集复扫

## 一句话结论

在「只能用什么」由外部规定、而不是由编译器规定的代码库里改代码（课程作业、甲方规范、内部基线、安全红线），先用两份权威语料抽出一份**属性/组件词表**，动手前拿它筛掉超纲写法，动手后再跑一次差集复扫——这比让 AI 凭印象判断"这算不算超纲"可靠得多。

## 触发条件与影响

- 项目或功能：给一个受课件/规范约束的工程做 UI 或功能改造，验收人是第三方（老师、甲方、评审）
- 环境与版本：任意；本次实测在 HarmonyOS ArkTS 工程，语料是 5 份官方快照（175 个 `.ets`）+ 已对齐规范的自有代码（28 个 `.ets`）
- 触发条件：改造引入了规范语料里从未出现过的 API（本次是 `linearGradient`、`shadow`、`stateStyles`、`animation`、`DotIndicator`、`LoadingProgress`、`AlertDialog`、`borderWidth`、`lineHeight`、`barHeight`、`placeholderFont`、`caretColor`、`Color.Transparent`）
- 影响范围：编译器全绿、构建全过，但交付物被判定"不像本阶段学的东西"——**这类问题编译期永远抓不到**

## 做法（可复制）

1. 定两份语料：① 权威样例（官方示例/老师发的快照/上游参考仓库）；② 自己已经通过验收的那部分代码（用 `git archive` 导出到临时目录，避免混入本轮改动）。
2. 抽词表：正则取 `\.([a-zA-Z_$]\w*)\(` 得属性名，取 `^\s*([A-Z]\w*)\(` 得组件名，两份语料并集 = 允许词表。
3. 对本轮代码做差集，输出「不在词表里的名字」。
4. **关键一步**：差集里的每一项先判断是不是自己起的方法名/`@Builder` 名（`typeCell`、`rowCell` 这类），再决定撤不撤——否则会把自造名字误报成超纲。
5. 撤 API 之后立刻补被它承担的职责（见下条记录的坑）。

## 证据

```
属性不在课件词表里 = ['SearchBar', 'count', 'countBtn', 'goodsCard', 'rowCell']
组件不在课件词表里 = ['SearchBar']
（课件侧属性词表 160 项，组件 42 项）
```

差集只剩自造的 `@Builder`/方法名 ⇒ 判定"本轮改动全部在允许写法内"。撤除前的同一脚本输出曾列出 14 个真超纲属性，逐项 grep 计数在两份语料里都是 0。

## 可复用规则

- 词表要**同时含自有已验收代码**，只看官方样例会把项目里早就存在的合法写法误杀。
- 词表是"允许集合"，不是"必须集合"：差集为空只说明没超纲，不代表功能正确。
- 每次改造完都要重跑差集，别只在开工前跑一次——中途补的样式最容易夹带新 API。
- 报告里把"未证实"的层级写清楚：本次能证明的是"写法在语料内 + 编译通过"，渲染效果仍需在设备上看。

## 适用范围与不适用范围

- 适用：课程作业、企业基线代码库、安全红线约束的模块、给第三方评审的交付物
- 不适用：自由选型的新项目；也不能用来替代功能测试

## 剩余风险

词表来自"样例里出现过"，若规范文档还教了别的写法但样例没写，会被误判为超纲（本次靠自有代码语料兜住）。解决办法是把第三份语料（官方图文/文档原文）也纳入并集。
