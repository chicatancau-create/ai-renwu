# 问题：给采集功能写「支持哪些能力」时容易把没验证过的写成支持；同时两处数据口径打架，界面显示的条数是虚的

> 来自一个已完成并归档的群消息采集工程（原目录已删除，代码在私有仓库）。适用于一切「对外声明能力边界」的采集/爬取类项目。

## 一句话结论

能力矩阵只有 **supported / partial / unsupported / not_verified** 四档，`not_verified` 不是 `unsupported` 的委婉说法，
它是「我还没量到」——把它写成任何肯定语气就是伪造验收。**红线词「实时」「全历史」「不漏消息」在拿到跨天分页证据之前一律不许出现在界面或文档里。**
另一件事：只要库里是「只追加的事件表 + 可重建的投影表」，**所有统计都必须走同一个「只算最新版本」的谓词**，
否则同一份数据会在两个接口报出 559 和 288 两个数。

## 触发条件与影响

- 项目或功能：给采集模块做能力自检页 + 对外 API 文档 + 界面统计卡片
- 环境与版本：SQLite（WAL）+ SQLAlchemy async + FastAPI；前端 react-query，无路由（视图名存 localStorage）
- 触发条件：
  1. 凭「接口看起来能返回数据」就写 supported；凭「看起来不支持」写 unsupported
  2. 事件表追加字段后触发重放，产生新版本行，而各统计查询各自决定要不要去重
  3. 探针为省事拦截第三方接口的非 GET 请求
- 影响范围：界面统计虚高一倍（今日样本 166 实为 67）；文档里的能力承诺无法兑现；拦截非 GET 导致被采集方页面直接报「服务异常」，
  被误判成平台不具备该能力（**一次假阴性差点把可用功能写成 unsupported**）

## 复现步骤

1. 前置条件：只追加的事件表，每行带 `(会话, 消息ID, version)`
2. 操作或命令：
   ```python
   # 给事件 payload 增加一个 content_raw 字段（append-only，等于给已有消息各写一行新版本）
   # 然后分别调两个接口
   GET /sources      -> count = 559
   GET /messages     -> total = 288
   ```
3. 预期结果：两处口径一致
4. 实际结果：差 271；主题聚合与打分同样把被取代的旧版本算进去，今日样本 166（虚）→ 67（实）

## 证据

**口径统一（实测）**

```
统一谓词 latest_version_only() = NOT EXISTS (同消息的更新版本)
四处共用：主题日聚合 / 打分入库 / 接口 sample_size / 列表总数
结果：/sources 与 /messages 从 559 vs 288 收敛到一致；今日样本 166 → 67
回归：新增一条「加字段后计数不变」测试，防止第三次踩同一坑
```

**能力矩阵终态（实测）**

```
supported    3 项（有真机取证：读到当日消息 / 可解码文本 / 可检索展示）
partial      1 项（补齐历史缺口：能翻页但从未跨过 00:00，故不写成全历史）
not_verified 9 项（Kuaishou 全线、实时推送、发送者画像等，一律标注「未验证」）
判据自检：supported 的匹配要用词边界，早期用 /supported/ 会命中 unsupported 内部子串造成假全绿
界面顺序：由响应里的 capabilityEntries() 派生，不在前端硬编码，避免矩阵漂移
```

**「只有 3 条」的反例（实测）**

```
用户质疑「怎么可能只有三条」→ 深翻后当日实际 288 条（221 + 67 两天口径，247 条含可读文本，21 个发送者）
结论：条数异常偏低时，先怀疑自己的取数与解码链路，不要写进矩阵当「平台限制」。
```

**拦截非 GET 的代价（A/B 对照）**

```
严格模式（拦掉非 GET）→ 被采集页面显示「服务异常」→ 探针取不到数据 → 差点记为 unsupported
放行模式（只记录 observed_non_get）→ 页面正常，功能可用
规则：观测型探针默认不改道，只分类记录；要拦必须显式开严格模式并说明副作用
```

**隐私边界落到代码（实测）**

```
导入器只处理授权会话 ID，其余会话的报文丢弃并计数 other_conversations_dropped
登录态目录 / 原始报文 / 库文件 全部 gitignore ⇒ 推存档仓库时这些一概不随行
（外发前的脱敏三查不在本条，见 [[规则-仓库公开前脱敏须扫全历史且改证据要重签哈希清单]]）
```

## 根因分析

- 已确认的根因：
  1. 「能力」是被测量出来的，不是被推断出来的；矩阵里每一格都要能指回一条取证记录。
  2. 只追加存储下，**任何没走最新版本过滤的统计都是错的**，而且错得安静（数只会偏大，不报错）。
  3. 探针改变了被测系统的网络条件，被测方就会给出与真实使用不同的响应，此时得到的「不支持」是探针造成的。
- 排除过的假设：
  - 不是数据库重复写入：行数差恰好等于被取代版本行数，去重后一致。
  - 不是接口缓存：直连库查询同样给出 559。
- 问题归属：本次工程实现引入（统计查询各写一套），非依赖或环境问题。

## 最小修复

1. 矩阵四档固定，`not_verified` 必须带「未验证」字样与缺哪条证据；红线词进白名单校验，界面文案不出现「实时/全历史/不漏」。
2. 抽一个共享谓词（`latest_version_only`）给所有聚合、打分、接口统计复用，注意别和同名查询参数冲突（接口层用别名导入）。
3. 观测脚本默认不改道：只分类记录非 GET，严格拦截另设开关。
4. 采集代码里**不留真实标识符**：夹具用同形状的合成值，真实 ID 只出现在运行期配置里；
   外发前的脱敏三查按 [[规则-仓库公开前脱敏须扫全历史且改证据要重签哈希清单]] 执行。
5. 隐私硬约束落到代码：只处理授权会话 ID，其它会话在导入器里丢弃并计数（`other_conversations_dropped`），
   登录态目录与原始报文一律 gitignore。

## 可复用规则

- 采集类工程交付前先写一张四档矩阵，每格后面挂一条可复跑取证命令；填不满的格子留在 `not_verified`，不许留空或写「应该支持」。
- 只要存储是只追加的，项目里就必须只有**一处**定义「最新版本」，其余全 import 它。看到两处去重逻辑就当 bug 报。
- 两个接口同一指标不一致时，先假设自己在数旧数据，而不是先怀疑对端。
- 观测第三方系统的脚本，默认「只读不改道」；任何拦截/改写都要在报告里注明它可能改变被测方行为。
- 代码要外发（推仓库、发人）之前，脱敏三查按 [[规则-仓库公开前脱敏须扫全历史且改证据要重签哈希清单]] 走；
  本条只补采集场景特有的一点：**夹具里不写真实标识符**，一律同形状合成值。

## 适用范围与不适用范围

- 适用：带对外能力声明的采集/接入类工程；事件溯源/只追加表；需要外发代码存档的场景
- 不适用：纯内部一次性脚本（无对外声明则矩阵可省）；不可变表且无版本重放的存储（无翻倍风险）

## 剩余风险

- `not_verified` 的 9 项若要转正，需各自补真机取证；本轮未做，转正在代码存档里保持未完成状态。
- 采集仍需人工在浏览器里登录并打开目标会话，无法无人值守；界面文案已按此事实写免责声明，但换号/换环境需重跑取证。
