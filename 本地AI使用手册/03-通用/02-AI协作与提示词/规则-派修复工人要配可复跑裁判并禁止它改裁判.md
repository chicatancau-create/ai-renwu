# 问题：给子代理派修复任务时，brief 里的措辞与「谁来判绿」决定了它会不会去修真正的问题

> 一次会话里 5 个工人、6 条经验。最贵的一条是：**我把一条外观约束写进了「必须保持」，工人就据此拒绝修一个真实缺陷。**

## 一句话结论

派修复任务前先把它变成**一个可复跑的裁判脚本 + 一句「禁止改裁判脚本」**，brief 里只写「必须达到的量化判据」，不写「必须保持现状」这类会被工人拿来当挡箭牌的外观约束；工人报完 PASS/FAIL 我独立复跑一次再采信。

## 触发条件与影响

- 项目或功能：Vue 3 习惯打卡应用（3 个工人并行写界面层）+ 两轮响应式/遮挡修复 + Word 登记表排版
- 环境与版本：Qoder 子代理（`Agent` 工具，`general-purpose`）、Windows + Git Bash
- 影响范围：修复是否发生、并行是否冲突、交付物里是否混进杂物、结论是否可信

## 六条实测经验

### 1. 文件归属互不重叠 + 契约写进 brief，三个工人并行零冲突

界面层拆成三个工人，brief 里各自列出「你负责的文件（只能创建/修改这些）」和「同事正在并行创建、你只需按路径引用、绝对不要创建或改动的文件」，并把跨文件契约钉死（props 名、emit 事件名、导出函数签名、类名）。结果：13 个文件、3505 行一次成型，构建直接通过，没有互相覆盖。

反例风险：我给 W3 的契约里写了同事文件路径，W3 回报时主动指出「按 push 时 HabitStats/HabitAbout/HabitLogin/MonthHeatmap 尚未落地，构建必然失败，属预期，不是我要修的」——**把「并行期构建会红」写进 brief，能避免工人去补别人的洞。**

### 2. 外观约束别写进必须项（本次最贵的一条）

我给修复工人 W5 的判据里写了「**1280px 下的版面观感不得退化**」。W5 量出桌面档 `.stats` 内容被操作列压住 26–33px，但判定「修它必然改动 1280 轨道宽度，与『1280 保持现状』冲突，故只报告不动」。

而那个遮挡在我自己的实拍图里看得见（「最长 6 天」被「编辑」吃掉半截）。**是我的一句话把正确修复挡在了外面。**

处置：把遮挡像素量 `cover` 直接加进裁判脚本、把 901/1024 两档也加进视口列表，再重新派单——判据变硬之后，W5 用「统计列内部两行化 + 轨道改成与内容无关」同时满足了 `over=0` 和 `cover=0`。

**规则：brief 里只写「必须达到的量化判据」；凡是不希望被拿来当借口的软要求，要么删掉，要么先量化成判据。**

### 3. 裁判脚本必须禁止工人改动

brief 原文：`不要改 C:\tmp\vuedoc\measure.mjs（那是裁判，改它等于作弊）`。同时提醒「预览服务读的是 `dist/`，改完源码必须重新 build 才量得到」——否则工人会改完源码直接跑裁判，量到的还是旧构建，报出一个假绿。

### 4. 工人报的 FAIL 也可能是我的探针错

W1 回报「4 个习惯行」，我的探针报 `rows=8` 判 FAIL。复核发现是我的 `[class*=row]` 同时命中 `.habit-row` 与 `.row-actions`。**先怀疑判据，再怀疑工人和产品。** 详见 `01-前端/09-测试与质量/踩坑-自写CDP探针的七种假阳性-真浏览器取证.md`。

反过来，W4/W5 报的「24 组合全绿」我独立复跑一次，确实全绿——复跑的成本是 1 分钟，不复跑的成本是把别人的结论写成交付。

### 5. 拍交付截图要和破坏性测试分开跑

W6（Word 排版）直接取了验收脚本跑完的截图，于是登记表里图 2 显示 4 行习惯、图 4 显示「习惯总数 3 个」——因为同一轮里先加了 1 个又删了 2 个。逐页目视复核才抓出来。
处置：单独写一个 `capture-shots.mjs`，先 `localStorage.clear()` 重新播种，按顺序拍完再退出，全程不做增删改。

### 6. 交付前要扫被测项目的根目录

本次工人往项目根扔了 `to_pdf.ps1`（W6），我自己扔了 `check-sfc.mjs`（语法闸门）。W2 曾建 `tmp-smoke/` 后自删并在回报里点名提醒。
规则：**收尾时 `git status` 看项目根，凡是本轮临时脚本一律移出或删除**；临时产物统一放 `C:\tmp\<会话名>\`，别让工人往被测项目里写。

另外：`evidence/` 里只放现场生成的产物（断言日志、实拍图），不要手写结论；一次性复用工具落 `tools/<工具名>/`，代码不进学习笔记库。

## 附带确认的一条能力边界

用户限定「只用 Kimi K3.1 PRO 和 Qwen3.8-flash 两个模型」。实测：`Agent` 工具**没有 model 参数**，子代理模型写死在 Agent 定义里；`list_agents` 与 `manage_app_agent list` 在本机只暴露 `qfmodel`（默认）与 `opus`（code-simplifier），没有那两个模型。`create_chat_session` 继承当前会话模型。
结论：要么由用户在设置里先建好两个指定模型的自定义 Agent（我能按名字派活），要么放弃模型名、只保留「大脑出契约不下场、工人动手」的结构。本会话选了后者并**在开工前就说明**，没有假装用上了那两个模型。

## 证据

- 13 文件 / 3505 行一次成型，`npm run build` 通过（三工人并行）
- W5 修前 `cover=26~58px`、修后 24 组 `over=0 且 cover=0`，我独立复跑一致（Edge 157，2026-11-15）
- 最终验收：`PASS=50 FAIL=1（故意的负对照）NOT_EXECUTED=1`，页面异常 0
- 项目根清理：`check-sfc.mjs`、`to_pdf.ps1` 已删，`git status` 只剩预期改动
- 并发提醒：本次另一会话同期在本仓库提交了 `a69999f`、`96c24e9`、`f8f4d19`（把习惯打卡模块收拢入库），所以我全程**没有做任何 git 提交**，避免把别人的未提交改动卷进来

## 根因分析

- 已确认的根因：brief 里的软性外观约束会被当作「不许动」的硬约束；判据不量化时工人会保守
- 排除过的假设：W5 并非能力不足——它给出了加宽轨道不可行的算术证明（901px 档四列地板之和会超过行宽），说明它判断过修法，只是被约束拦下
- 问题归属：本次修改引入（brief 是我写的）

## 最小修复

brief 模板调整三条：① 必须项只写量化判据；② 显式禁止改裁判脚本；③ 提醒「构建产物驱动 → 改完要 rebuild」。

## 验证记录

- [x] 重新派单后 W5 同时满足 `over=0` 与 `cover=0`，且 1280px 轨道逐列相等（未退化）
- [x] 我独立复跑裁判，与工人回报一致
- [x] 交付前 `git status` 项目根无本轮临时脚本残留
- [ ] 「模型名无法指定」这条未验证是否可通过新建自定义 Agent 绕过（需用户操作）

## 可复用规则

1. 派修复任务：先写裁判脚本，再写 brief；brief 只引用判据数字，不写「保持现状」。
2. 并行分工：列出「你只能碰的文件」+「同事会创建、你只引用不要建」+ 跨文件契约（props/emit/导出/类名）。
3. 裁判脚本对工人只读；提醒构建产物与源码的时间差。
4. 工人报绿 → 我复跑；工人报红 → 我先证伪自己的判据。
5. 交付截图单独一趟，跑在干净种子态，不做破坏性操作。
6. 收尾扫被测项目根目录，临时脚本一律清掉；证据进 `evidence/`，工具进 `tools/`。
7. 多会话共用仓库时，**开工与收尾各重测一次 `git log`/`git status`**，并默认不提交。

## 适用范围与不适用范围

- 适用：给任何子代理/协作者派「修复 + 验收」类任务；并行分工；交付物含截图或排版产物
- 不适用：纯问答、无产物任务；已有 CI 门禁能自动判绿的项目（判据由流水线持有，不需要手写裁判）

## 剩余风险

- 「禁止改裁判」靠文字约束，没有技术强制；更稳的做法是把裁判放在工人无写权限的位置（本次未做）
- 模型选择能力可能随 Qoder 版本变化，引用本条前先重新 `list_agents` 核对
- 「不提交」在多会话并发下是安全默认，但会让本轮改动长期停留在工作区，需要用户自己收拢（本次确实由另一会话代为提交）
