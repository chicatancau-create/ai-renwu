# 问题：多 AI 同仓的审查交接三件套与会话续接先核时钟

## 一句话结论

审查方与执行方共用一个仓库时，交接靠三件套（「续接后现状结论作废」的主记录见 [[踩坑-多会话共享仓库致提交搭车与现状结论作废]]，本条补充审查交接视角与核时钟动作）：**发现文档（每条带 file:line 与可复跑脚本）+ 执行方必读文档里的指针 + 逐条处置建议（做法/坑/验收 gate/优先序）**；已闭项标 ✅、另列「不要重查/不要追」清单。会话被压缩续接后，上一轮的「现状」结论默认作废，先跑 `date` + `git log` + 目标文件行数重测再下结论。

## 触发条件与影响

- 项目或功能：一个仓库由多个 AI 会话并发读写（本机 CodeWeave：审查方 + 执行方）。
- 环境与版本：Git Bash；会话可能被压缩续接，真实时间可能比上下文里的时间晚数天。
- 触发条件：审查方把发现只写在对话里、或续接后沿用旧现状结论。
- 影响范围：执行方看不到发现或照过期结论改;审查方基于过期事实下错判断（本会话曾两次：把 5 天前的「4 页/229 行」当现状;把 2 天前的门禁状态当现状）。

## 复现步骤

1. 前置条件：审查方产出发现；执行方独立推进;会话续接。
2. 操作：A 只把发现写对话里；B 续接后直接引用上一轮现状。
3. 预期：执行方收到并处理;现状判断正确。
4. 实际：A 的发现执行方看不到；B 的现状结论过期（HEAD/行数/门禁都已变），据此给出的缺口判断错误。

## 证据

- 三件套生效：审查文档 + 待办指针 + 处置建议落地后，执行方在数小时内按建议关闭 B1（等值令牌手法）、B2、并自行修掉 A1；B3 由审查方按用户指示直接写入。证明「写进必读文档 + 给可执行处置」比「写在对话里」有效。
- 时钟漂移两次实测：上下文时间为 10-11 而真实 11-09（差 29 天，HEAD 与 QML 行数全变）;上下文 11-11 而真实 11-12（门禁与未闭项状态已变）。两次都靠 `date` + `git log -1` + `wc -l` 纠正。
- 相对 mtime 的陷阱：用「N 分钟前」判断活跃度可以，但用它推断「今天是哪天」会错;曾把 25 小时前的写入当噪声。

## 根因分析

- 已确认的根因：对话不是执行方的输入通道;续接不携带真实时钟;相对时间差不等于绝对日期。
- 排除过的假设：不是执行方「不读文档」——指针放进必读文档后它确实照做。
- 问题归属：协作方法（修改前已存在的认知陷阱）。

## 最小修复

1. 发现写成独立文档，放执行方必读清单指向的位置，并在必读文档顶部加指针段。
2. 每条发现给：file:line、违反的条款、可复跑检索脚本、处置建议（做法/坑/验收 gate）、优先序。
3. 已闭标 ✅ 附复核依据;列「不要重查」「不要当缺口追」清单，避免执行方重复劳动或扩大范围。
4. 续接后第一条现状类回答前，跑 `date`、`git log -1`、目标文件 `wc -l`，与上一轮数字对比;变了就作废旧结论。

## 验证记录

- [x] 格式化或静态检查：不适用。
- [x] 类型检查或编译：不适用。
- [x] 单元、集成或端到端测试：不适用。
- [x] 构建：不适用。
- [x] 启动或手动回归：执行方按三件套关闭 B1/B2/A1 的行为即回归证据；两次时钟漂移均被重测纠正。

## 可复用规则

审查交接 = 发现文档 + 必读指针 + 处置建议；续接 = 先核时钟与 HEAD 再谈现状。适用：多 Agent 共仓、长会话续接。例外：单会话短任务无需三件套，但核时钟仍建议保留。

## 适用范围与不适用范围

- 适用：多 AI 同仓审查/执行分工；被压缩续接的长会话。
- 不适用：执行方与审查方同一会话（发现直接进对话即可）。

## 剩余风险

执行方可能只关「容易的」而留下阻塞项（本会话 A2 长期未闭）；处置建议里必须显式标出唯一阻塞项与负对照 gate，否则容易被跳过。
