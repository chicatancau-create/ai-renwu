# 问题：改窗口样式「看起来成功、其实没生效」，因为宿主进程是提权的

## 一句话结论

宿主程序（`D:\open-revo\open-revo.exe`）**以管理员身份运行**时，普通权限的守护进程调 `SetWindowLongW(hwnd, -20, ...)` 给它加 `WS_EX_LAYERED | WS_EX_TRANSPARENT` 会被 **UIPI 静默拒绝**（返回 0、`GetLastError()=5 ERROR_ACCESS_DENIED`，`SetLayeredWindowAttributes` 同样 False err=5）；而老代码把**算出来的目标值**当结果返回，于是状态文件里恒为「已生效」——面板绿字是假的。正解是让**页面自己**调宿主提供的 `set_click_through { enable }` 接口。

## 触发条件与影响

- 项目或功能：OpenRevo MRO HUD 浮条的「锁定 / 分层穿透」
- 环境与版本：OpenRevo v0.9.8（宿主 PID 提权，`TokenElevation` 查得 `ELEVATED`），守护 `pythonw.exe` 为普通完整性
- 触发条件：任意跨进程 `SetWindowLongW(GWL_EXSTYLE)` / `SetLayeredWindowAttributes` 目标窗口属于提权进程
- 影响范围：样式位写不进去，但**代码以为写进去了**；UI 显示「分层穿透已就位」，实际点击仍被浮条吃掉，用户完全看不出问题在哪

## 复现步骤

1. 前置条件：宿主以管理员启动，浮条窗口存在（`title='OpenRevo - MRO HUD' class='Window Class' 490x104`）
2. 操作：从普通权限 Python 调
   `ctypes.windll.user32.SetWindowLongW(hwnd, -20, cur | 0x80000 | 0x20)`
3. 预期结果：返回新的 exstyle，含 `WS_EX_LAYERED`
4. 实际结果：返回 `0`，`GetLastError()=5`；连采 60 次 `GetWindowLongW(hwnd,-20)` 恒为 `0x00040118`（既无 `0x80000` 也无 `0x20`），3 秒内不变

## 证据

- `SetWindowLongW` → `0`，`Marshal.GetLastWin32Error()=5`
- `SetLayeredWindowAttributes` → `False`，err `5`
- exstyle 采样恒为 `0x00040118`
- 守护日志：`style write denied by OS (host elevated); click-through delegated to hud page`
- 提权判定（ctypes，无需管理员）：
  ```python
  h = ctypes.windll.kernel32.OpenProcess(0x1000, False, pid)
  tok = ctypes.c_void_p()
  ctypes.windll.advapi32.OpenProcessToken(h, 0x0008, ctypes.byref(tok))
  buf = ctypes.create_string_buffer(4); n = ctypes.c_ulong()
  ctypes.windll.advapi32.GetTokenInformation(tok, 18, buf, 4, ctypes.byref(n))
  elevated = bool(ctypes.cast(buf, ctypes.POINTER(ctypes.c_ulong)).contents.value)
  ```

## 根因分析

1. Windows **UIPI（User Interface Privilege Isolation）**：低完整性进程不能给高完整性进程的窗口写样式（`SetWindowLong`/`SetLayeredWindowAttributes` 都被拦），这是安全设计，不是 bug。
2. 老代码的 `apply_style()` 末尾 `return target`（**计算出来的目标 exstyle**），调用方据此置 `STATE["layered"] = bool(ex_after & WS_EX_LAYERED)`、`applied = layered == transparent` ⇒ 恒真，形成「假绿」。
3. 宿主自己给自己窗口加穿透不受限制，所以宿主内置了 `set_click_through { enable }` / `get_click_through` / `toggle_click_through` 三个命令（二进制 Rust 命令注册表里可见，参数名 `enable`），插件页还能拿到 `window.setClickThrough()` 便利方法。

## 修复

三处一起改（脚本在 `G:\AIrenwu\OpenRevo插件整理\工具\`，均幂等）：

1. `patch_mro_ct_readback.py`：`apply_style` 末尾改成 `return get_ex(h)` **读回真实值**；主循环里 `if transparent and not STATE["applied"]:` 把原因写进 `STATE["error"]` 并只记一次日志。
2. `patch_hud_clickthrough.py`：浮条页面新增 `syncClickThrough(want)`，优先 `window.setClickThrough(want)`，回退 `invoke("set_click_through",{enable:want})`；在状态更新处调 `syncClickThrough((nextLocked || nextHidden) && !nextCtrl)`。
3. `patch_mro_panel_ct_text.py`：面板文案区分「穿透由浮条页面接管」/「分层穿透已就位」/「未就位」。

## 验证

- 只做上面三步时，`ct_state.json` 会变成诚实的 `layered=false applied=false` + `error="风格改不动（宿主以管理员运行）；穿透已交给浮条页面走宿主接口"`
- 日志出现 `style write denied by OS (host elevated); click-through delegated to hud page`
- `hud.html` 内联脚本抽出来 `node --check` 通过

## 第二坑：判定穿透别用 `WS_EX_LAYERED`（0x80000），要用 `WS_EX_TRANSPARENT`（0x20）

**症状**：上面三步修完之后，面板仍报「分层穿透未就位」，但用 exstyle 一测发现穿透其实**已经生效**。

**根因**：宿主 `set_click_through` 只给窗口加 `WS_EX_TRANSPARENT(0x20)`，**不加 `WS_EX_LAYERED(0x80000)`**。判定却写成 `applied = bool(ex & 0x80000) == transparent` ⇒ 永远判错。

**实测证据**（同一浮条窗口 `0x2c0c66`）：

| 状态 | exstyle | 含 0x20 | 含 0x80000 | 鼠标 |
|------|---------|---------|-----------|------|
| 锁定 `locked=true` | `0x00040138` | YES | no | 穿透（点不中） |
| 解锁 `locked=false` | `0x00040118` | no | no | 可拖拽 |

**修法**（脚本 `patch_mro_ct_passthrough.py` + `patch_mro_panel_ct_text2.py`）：
`STATE["passthrough"] = bool(ex_after & WS_EX_TRANSPARENT)`、`STATE["applied"] = STATE["passthrough"] == transparent`，并把 `passthrough` 写进状态文件；面板按 `applied` 显示绿字「穿透已生效」。

**通用教训**：判断「窗口是否鼠标穿透」看的是 `WS_EX_TRANSPARENT(0x20)`，`WS_EX_LAYERED(0x80000)` 只表示「窗口有分层属性（可用于整体 alpha）」，两者不是一回事，别混用。

## 剩余风险 / 注意

- 改了 `hud.html` **必须让页面重新加载**才生效（关掉浮条再显示，或重启宿主）；WebView2 不监听文件变更
- 宿主已提权时，本会话 `Stop-Process`/`taskkill` 都会被拒，只能 `(Get-Process -Id N).Kill()`（且对提权进程同样可能被拒）
- 同类推断：任何「跨进程给提权窗口改样式」的自动化（置顶、透明、去边框）都会踩同一个坑
- 判断穿透必须看 `WS_EX_TRANSPARENT(0x20)`，看 `WS_EX_LAYERED(0x80000)` 会误判（见上面「第二坑」）
