# 踩坑：测试"验证关机收尾"时真的执行了收尾，把系统代理清零

> `verified`：2026-11-11 在窗口居中项目里真实发生并当场恢复；同一台机器全机断代理约几十秒。

## 一句话结论

**被测逻辑只要会改"系统级状态"（注册表里的系统代理、服务、计划任务、HKCU Run），
测试就必须在 `import` 那一刻把那个副作用函数替换掉**，不能靠"我给传了个测试配置"。
本轮测试为了验证"取消关机要复位标志位"，直接调 `WM_QUERYENDSESSION` 分支，
而该分支**先关系统代理**——配置里没写 `disable_system_proxy`，代码默认值是 `True`，
于是 `ProxyEnable` 从 1 被改成 0，整机断代理。

## 触发条件与影响

- 项目或功能：`03_工具脚本\session_end.py`（`SessionEndGuard`：关机/休眠 → 关系统代理 + 退代理软件 + 唤醒重启）
- 环境与版本：Python 3.14；Windows 11；系统代理 `127.0.0.1:7890`（FlClash）
- 触发条件：测试代码 `g._on_message(0, WM_QUERYENDSESSION, 0, 0)`，且 `cfg` 里**没有** `disable_system_proxy` 键
- 影响范围：写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings\ProxyEnable=0`
  ⇒ 所有走系统代理的程序瞬间失联；`ProxyServer` 保留原值，所以**表面上配置还"在"**
- 发现方式：**不是我发现的**，是同批另一个测试的断言替我抓到 ——
  `test_new_rules_20261103.py` 有一条回归锁 `【D4】真实系统代理未被测试影响 FAIL ProxyEnable=0`。
  这说明"另有一条测试专门盯外部状态"是值得的。

## 复现步骤

1. `cfg = {"enabled": True}`（缺 `disable_system_proxy`）
2. `guard = SessionEndGuard(cfg, log, ...)`，`guard.start()`
3. `guard._on_message(0, WM_QUERYENDSESSION, 0, 0)`
4. 读 `HKCU\...\Internet Settings\ProxyEnable`：预期仍为 1，实际变成 0

## 证据

```
test_new_rules_20261103.py： 【D4】真实系统代理未被测试影响 … FAIL ProxyEnable=0
恢复前： ProxyEnable=0  ProxyServer=127.0.0.1:7890（值还在，开关被关）
恢复后： ProxyEnable=1  ProxyServer=127.0.0.1:7890（复查通过）
```

## 根因分析

- 已确认的根因：**默认值就是危险动作**。`cfg.get("disable_system_proxy", True)` 的默认是
  "关代理"，而测试只写了它关心的键 ⇒ 没写的键自动取了最危险的那个值。
  "测试用的配置"因此不是安全阀，测什么必须显式写什么。
- 排除过的假设：
  - "是别的程序关的代理"→ 否：时间点与测试执行严格对应，且同批 D4 断言当场失败。
  - "代理软件自己退出导致"→ 否：进程一直在跑，只有注册表开关变了。
- 问题归属：**我的测试写法**引入（不是产品代码的缺陷）。

## 最小修复

两道保险，缺一不可（都在测试文件里，不动产品代码）：

```python
# ① 导入即打桩：任何走到 _do_shutdown 的路径都不再碰真实注册表
_orig_disable = session_end.disable_system_proxy
def _fake_disable_proxy(*a, **k):
    CALLS.append((a, k))            # 只记录，绝不写注册表
    return True
session_end.disable_system_proxy = _fake_disable_proxy

# ② 造配置时把危险键显式关掉，避免"默认值踩雷"
def make_guard(cfg=None):
    cfg = dict(cfg or {})
    cfg.setdefault("disable_system_proxy", False)
    ...
```

恢复动作（万一又发生）：

```python
import winreg, ctypes
k = winreg.OpenKey(winreg.HKEY_CURRENT_USER,
                   r"Software\Microsoft\Windows\CurrentVersion\Internet Settings",
                   0, winreg.KEY_SET_VALUE)
winreg.SetValueEx(k, "ProxyEnable", 0, winreg.REG_DWORD, 1)
ctypes.windll.wininet.InternetSetOptionW(0, 39, 0, 0)   # SETTINGS_CHANGED
ctypes.windll.wininet.InternetSetOptionW(0, 37, 0, 0)   # REFRESH
```

## 可复用规则

1. 写测试前先列一遍"这段代码会产生哪些**被测进程之外**的副作用"（注册表 / 服务 / 计划任务 /
   自启动项 / 真进程 / 真文件），**逐个在 import 阶段打桩或改到临时键**。
2. 配置默认值要按"最坏后果"审视：凡是默认 = 破坏性动作的键，测试必须显式覆盖。
3. 留一条**专门盯外部状态**的回归锁（本例 D4：`ProxyEnable` 没被改），它比"日志里看起来没动手"可靠。
4. 触发领域事件用私有入口（`_on_message(...)`）时，要想清楚它是**只发通知**还是**顺手就干了活**。

## 适用范围与不适用范围

- 适用：任何测"关机/开机/退出/同步"等系统级收尾逻辑的测试；任何会写 HKCU/HKLM 的代码。
- 不适用：纯函数、只读探测（无副作用可言）。

## 剩余风险

- 打桩是按函数名替换，若产品代码改走别的路径（如新建 `_power_off()`），打桩会失效而测试"照样绿"。
  → 需要一个断言：测试结束核对 `CALLS` 里确实记到了预期次数，否则报"打桩未被走到"。

## 同一族的第二面：端到端脚本会移动用户**真实**窗口（2026-11-14 补）

上一节是"测试顺手做了破坏性系统动作"，这一节是"测试顺手改了用户桌面"——同一条纪律的另一面，实测踩到了：

- `03_工具脚本/e2e_verify.py:73` 直接调 `watch.scan_once(cfg, stable, handled, priming=False, ...)`。
  这个函数**扫的是当前整个桌面的真实窗口**，不是测试自建的窗口，于是它会真的把用户开着的应用
  移动/缩放到红圈里。证据：跑完 e2e 后 `watch.log` 多出一条
  `11-14 19:55:12 加宽居中 WorkBuddyAI.exe 2202x1340->1718x1340`，而那条不是常驻监视器写的。
- **危害不是"数据错"，而是"用户正在用的窗口突然跳位"**，且很难归因（看起来像监视器抽风）。
- 修法与判据：
  1. 端到端脚本要移动窗口就**自己造窗口**（本例 `e2e_verify.py` 早期版本就是自建窗口），
     不调会扫全桌面的入口；必须调时把 `priming=True` 或把作用域限制到指定 hwnd。
  2. 跑 GUI 类测试前先判**用户是否在操作**（`GetLastInputInfo` → 空闲时长）；
     用户活跃就别跑会抢桌面的用例，或直接跳过并打印原因。
  3. 验收时把"日志里出现的动作"和"我以为测试只做了什么"对一遍——多出来的动作就是副作用。
