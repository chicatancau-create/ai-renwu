# 经验：扫描版 PDF 没有文字层时，唯一可靠的「全量扫完」证明是页数对账

> `verified`：三本扫描书共 2535 页全部识别完成，页数与原书一一对应，空页逐页人工复核。
> 本文只记录**这条管线怎么做、怎么证明没漏**，不记录任何一本书的内容。

## 一句话结论

扫描版 PDF（`get_text()` 抽不出字）要「全量提取且可证明无遗漏」，必须走三段：
**① 先导出 PDF 书签当唯一结构真相 → ② 用 PyMuPDF 2 倍渲染 + RapidOCR 逐页识别，每页落 `## pN` 页码锚，`_done.txt` 断点续跑 → ③ 用「输出页数 = 原书页数」双向对账 + 空页人工复核 收尾。**
OCR 出来的标题**不能**当目录用，目录只能来自书签。

## 触发条件与影响

- 项目或功能：把纯扫描的教材 PDF 转成可检索的 Markdown 文本层，供后续知识库下钻引用。
- 环境与版本：Windows；Python + `pymupdf` + `rapidocr_onnxruntime`（ONNX CPU 推理，无需 GPU）。
- 触发条件：`page.get_text()` 抽样返回空串或只有零星空白字符 ⇒ 判定为纯图片 PDF。
- 影响范围：漏页不会报错、也不会中断，**只看"脚本跑完了"会把缺页当成成功**。

## 复现步骤

1. 前置条件：拿到扫描版 PDF，先抽样 3~5 页调 `get_text()`，确认确实无文字层。
2. 导出书签当结构：

```python
import pymupdf
doc = pymupdf.open(pdf)
toc = doc.get_toc()          # [level, title, page, ...]
with open("toc.txt", "w", encoding="utf-8") as f:
    for lvl, title, page in toc:
        f.write(f"{'  ' * (lvl - 1)}{title}\t p{page}\n")
```

3. 逐页渲染后识别：

```python
pix = page.get_pixmap(matrix=pymupdf.Matrix(2.0, 2.0))   # 2 倍足够，别上 4 倍
img = pix.tobytes("png")                                  # 或转 numpy (h,w,n) 喂 OCR
result, _ = ocr(img)
lines = [t[1] for t in (result or [])]
```

4. 每页写一个页码锚，输出形如：

```text
## p12
（正文……）
```

5. 预期结果：页数与原书一致，标题层级与书签一致。
6. 实际结果：三本书 966 / 775 / 794 页，合计 **2535 页**全部产出，与原书页数逐本相等。

## 证据

- 三本书均无文字层，`get_text()` 抽样全空。
- 书签条数：677 / 175 / 312，作为章节结构唯一来源。
- 识别速率实测约 **3.8 秒/页**，平均约 **1088 字/页**，全量约 **282 万字**，总耗时约 2.5 小时。
- 中途在第 268 页进程 `exit -1`（疑似渲染/推理内存峰值），因脚本设计 `_done.txt` 记录已完成页，重启后自动从断点续跑，最终无缺页。
- 收尾核对：三本页数与原书 966/775/794 一一对应，无缺页、无重复页、无 `OCR ERROR` 页。
- 20 处「近空页」逐页人工确认，全部是章节扉页/整页插图，不是漏识别。

## 根因分析

- 已确认的事实：纯图片 PDF 没有文本层，`get_text()` 不是"抽得少"，而是**结构上就没有字**；只能靠视觉识别重建文本。
- 为什么书签必须单独落地：OCR 对标题的识别错字率明显高于正文（大字号加粗、字距异常），拿 OCR 结果反推章节会得到错目录；而 PDF 书签是出版方写入的，页码与标题都准确。
- 为什么必须断点续跑：2535 页的长任务会撞内存峰值或驱动异常，`exit -1` 不可预测；没有完成清单就只能整批重跑。
- 排除过的假设：加渲染倍率不能修漏字（2 倍已可读，4 倍只变慢且更容易 OOM）；换 OCR 引擎不能修结构问题（任何 OCR 都会错字）。
- 问题归属：任务设计层面（缺少对账与续跑），不是某一行代码的 bug。

## 最小修复（可复用管线）

1. **先结构后正文**：`get_toc()` 落地成 `toc_*.txt`，作为目录权威源；OCR 只负责正文。
2. **固定渲染参数**：`Matrix(2.0, 2.0)`，pixmap 转 numpy `(h, w, n)` 直接喂 `RapidOCR`，不做二次压缩（压缩会掉小字）。
3. **每页落页码锚**：`## pN` 与原书页码一致，后期任何引用都能回查原书第几页；空页写一句「（本章扉页/插图/空白页，无正文文字）」，避免被当成失败。
4. **完成清单**：每页成功即追加到 `_done.txt`，启动时跳过已完成的页；这是唯一能在崩溃后不重跑整批的机制。
5. **对账收尾**（缺一不可）：
   - 输出 `## pN` 的条数 == 原书页数；
   - 书签标题条数 == 输出里的标题条数（允许 ±1 的排版误差）；
   - 列出所有「近空页」（字符数低于阈值），逐页人工确认是扉页/插图。
6. **产物分层**：原始 OCR 文本是中间件，最终只保留加了页码锚的 Markdown；中间件在核对完毕后清掉，避免两套真相。

## 可复用规则

1. **判"是不是扫描件"只看 `get_text()` 抽样，不看文件大小或页数。**
2. **目录只信 PDF 书签，不信 OCR 标题。** OCR 越像正文越好用，越像标题越不可信。
3. **长任务必须有完成清单**（`_done.txt` 之类），并且清单要在"这一页确实写盘成功"之后才追加。
4. **"跑完了"不是完成证据**，完成证据是**页数对账 + 空页人工复核**。
5. **每页留页码锚**，否则后期引用无法定位到原书页，文本层就失去溯源价值。
6. **中间件与交付件分开**，交付后删中间件，避免同一内容两份真相。

## 适用范围与不适用范围

- 适用：纯图片 PDF（扫描书、影印件、图片导出的 PDF）转文本层；需要"可证明无遗漏"的批量 OCR。
- 不适用：本身有文字层的 PDF（直接 `get_text()` 即可，OCR 反而引入错字）；手写体、竖排古籍、公式密集的排版（OCR 会系统性退化）。

## 剩余风险

- **OCR 必带错字**，尤其人名、专有名词、代码符号；文本层只能用于检索与定位，**引用原文仍应回查原书对应页**。
- 公式、表格、多栏排版会被压平成单行，结构信息丢失；需要公式/表格时得单独处理。
- 2 倍渲染对极小字号（脚注、图注）仍可能漏字，本轮未针对脚注单独加倍数。
- CPU 推理 3.8 秒/页是单机实测；换机器或换模型版本速率会变，工期估算要以本机实测为准。
