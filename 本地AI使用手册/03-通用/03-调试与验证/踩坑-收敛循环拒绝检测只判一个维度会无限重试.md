# 踩坑：只复核"尺寸被改回"，漏了"位置被改回" → 无限重启动画

## 一句话结论

任何"设置 → 复核 → 再设置"的收敛循环，**熔断判据必须覆盖你设置过的每一个维度**。
本次只复核了尺寸，没复核位置，于是"接受尺寸但拒绝移动"的窗口永远不触发熔断：
动画跑完 → 窗口没动 → 重新起动画，一直循环到宽限期结束，**白跑几十次、刷几十条日志**。

## 触发条件与影响

- 项目或功能：窗口居中/缩放常驻监视器（`watch.py`）。
- 环境与版本：Windows 11，Python 3.13，`SetWindowPos`。
- 触发条件：某些应用（实测 PixPin、`dm.resizer.exe`）**接受尺寸变化但拒绝位置变化**。
- 影响范围：每次这类窗口出现，`center()` 被调用 20~33 次、日志刷 20+ 条，持续到
  `settle_ms`(4s) 宽限期结束。用户看到的是日志暴涨与无意义的 CPU 占用。

## 复现步骤

1. 前置条件：程序同时设置**尺寸**和**位置**，并只在"下一轮"复核**尺寸**是否被改回。
2. 操作：让一个窗口接受尺寸、拒绝移动。
3. 预期结果：调整失败后熔断、收手。
4. 实际结果：动画 3 帧跑完 → 窗口位置纹丝不动 → 下一轮重新 `center()` → 再跑 3 帧 …

## 证据

`watch.log` 原文（同一 hwnd、**起点恒为同一坐标**，说明窗口根本没动）：

```
11-01 00:40:30 居中 PixPin.exe hwnd=0xf1260 类=Qt51513QWindow 1038x1280->1038x1280
               开始位移动画 3 帧 起点=(761,160) 终点=(761,130)
11-01 00:40:31 居中 PixPin.exe hwnd=0xf1260 ... 起点=(761,160) 终点=(761,130)
11-01 00:40:31 居中 PixPin.exe hwnd=0xf1260 ... 起点=(761,160) 终点=(761,130)
   （3 秒内 10+ 条，起点全是 761,160）

11-02 11:13:28 居中 dm.resizer.exe hwnd=0x580ef0 类=TfrmOem1 1076x745->1076x745
               开始位移动画 3 帧 起点=(741,428) 终点=(742,397)
   （2 秒内 20+ 条，起点全是 741,428）
```

统计：`dm.resizer.exe` 3 天内 71 次处理，`PixPin.exe` 累计 320 次（全库最高）。

## 根因分析

- 已确认的根因：熔断状态只记录 `(期望宽, 期望高)`，复核时也只比尺寸。
  位置从未进入判据，所以"位置被改回"这件事在系统里**不可观测**。
- 排除过的假设：不是 `SetWindowPos` 失败（返回值正常）、不是动画逻辑错
  （动画本身每帧都推进了）、不是宽限期没生效（4s 后确实会停，只是 4s 内空转几十次）。
- 问题归属：本次修改引入（熔断设计时只考虑了尺寸）。

## 最小修复

把复核记录从 `(期望宽, 期望高)` 扩展为 `(期望宽, 期望高, 期望 x, 期望 y)`：

```python
# 设置后
pending_check[hwnd] = (tw, th, tx, ty)

# 下一轮复核
want_w, want_h, want_x, want_y = pending_check.pop(hwnd)
size_bad = abs(w - want_w) > tol or abs(h - want_h) > tol
pos_bad  = abs(ext.left - want_x) > tol or abs(ext.top - want_y) > tol
if size_bad or pos_bad:
    reject_count[hwnd] = reject_count.get(hwnd, 0) + 1
    if reject_count[hwnd] >= stubborn_limit:
        log(f"熔断 ... 连续 {n} 次改了{'尺寸' if size_bad else '位置'}被改回，放弃调整")
        handled.add(hwnd)
```

**实测效果**：`center` 调用 **26 → 2** 次，日志 **26 → 1** 条，窗口正常进入 `handled`。

## 可复用规则

**写"设置→复核→重试"的收敛循环时，先列出你设置过的所有维度，逐一纳入复核。**

1. 设置了几维（尺寸 x/y、位置 x/y、透明度、层级…），复核就查几维。
2. 熔断计数要能区分"哪个维度失败"，日志里写出来，否则下次还是查不出。
3. 自测方法：造一个"只接受部分维度"的假对象，跑足够多轮，断言
   **调用次数 ≤ 阈值** 且**日志条数 ≤ 阈值**。只断言"最终收敛"会漏掉这种空转。
4. 日志刷屏是症状不是病：同一 hwnd、**同一"起点"** 重复出现，几乎必然是收敛判据有洞。

## 适用范围与不适用范围

- 适用：任何轮询式收敛循环（窗口位置/尺寸、UI 布局调整、配置下发重试、状态同步）。
- 不适用：一次性操作（不轮询就不会有这个问题）；幂等无副作用的纯计算。

## 剩余风险

若应用**部分**接受（例如尺寸到位但位置差 3px 以内），会被 `tolerance_px` 判为成功而不熔断，
这是预期行为（本来就在容差内）。
