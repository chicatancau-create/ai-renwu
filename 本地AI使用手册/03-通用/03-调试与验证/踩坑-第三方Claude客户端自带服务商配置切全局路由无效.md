# 问题：客户端"思考中"卡很久、后台看不到用量，切服务商路由没用

## 一句话结论

三条判据缺一不可：**① 谁在真正发请求**（看进程外网连接，不看界面）；**② 线路死活只能打一发最小补全请求**
（列模型接口不看余额，会报"正常"）；**③ 有些客户端自带服务商库，全局路由/系统代理对它无效**。

## 触发条件与影响

- 项目或功能：桌面 AI 客户端（本机 `D:\Claude Code Haha`）报"API Error: 402"后界面长时间"思考中"无输出。
- 环境与版本：Windows + cc-switch v4.0.4 本地代理 + clash-verge（mixed 7897）。
- 触发条件：把服务商在 cc-switch 里切换/排队，但客户端仍打自己配的地址。
- 影响范围：误判为"模型慢/在跑"，白等；或误判"服务商没用量=坏了"。

## 复现步骤

1. 前置条件：客户端自带服务商库（`~\.claude\cc-haha\providers.json` + `settings.json` 写死 `ANTHROPIC_BASE_URL`）。
2. 操作或命令：在 cc-switch 里把 claude 路由切到别家 → 客户端发一轮。
3. 预期结果：请求走新路由，新服务商后台出现用量。
4. 实际结果：cc-switch 日志里 `[Claude]` 转发行 **0 条**、代理端口只有 LISTENING 无 ESTABLISHED；
   客户端进程直连它自己配置的那家 IP。

## 证据

- `~\.cc-switch\logs\cc-switch.log` 全库 2129 条转发全是 `[Codex]`，`[Claude]` 零条。
- `netstat -ano` 按 PID 过滤：卡住的 9 分钟里 sidecar **零外网连接、CPU 增量 0.00s/5s**、工程目录零文件写入 = 假忙。
- 同一把 key：`GET /v1/models` → 200；`POST /v1/messages`（max_tokens=8）→ **402 insufficient balance**。
- 直连 vs 走代理对照：某服务商直连 3/3 `CONNECT_TIMEOUT`（10.5–15s），加 `NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://127.0.0.1:7897` 后 3/3 秒回 200。

## 根因分析

- 已确认的根因：① 该服务商余额为 0（402 只在 `/v1/messages` 露出）；② 客户端有独立服务商库，不读全局路由，
  也不读系统代理（`ProxyEnable=1` 后实测仍直连）；③ 本机到该服务商 IP 的直连链路丢包级抖动，必须走代理或 TUN。
- 排除过的假设：**DNS 污染已证伪**——Google DoH 与系统解析返回同一个 IP，是链路质量差不是解析错。
  "界面显示正常"也不能当证据（健康检查只列模型）。
- 问题归属：环境或依赖 + 客户端设计，非本次修改引入。

## 最小修复

排查顺序（便宜在前）：

1. 按 PID 看外网连接 + CPU 增量 + 目标工程目录 mtime → 先判"真跑还是假忙"。
2. 用最小 `POST /v1/messages` 判线路死活与余额，**不要用 `/v1/models` 的 200 下结论**。
3. 确认归属：查代理转发日志的 `[Claude]/[Codex]` 计数、`netstat` 里客户端实际连的 IP。
4. 需要代理时优先开 TUN（TUN 开关写进运行时配置但没出现虚拟网卡 = 服务模式没装，起不来）。

## 验证记录

- [x] 对照组：同一 key 分别打 models 与 messages，得到 200 与 402 两种结果。
- [x] 双路径：直连 3/3 超时、走 7897 3/3 成功，均带耗时。
- [x] 归属：代理日志计数 + 按 PID 的 netstat 双向印证。
- [ ] 修复后端到端：用户改配置后自行确认"能用了"；我方仅观测到空闲态（零连接、零写入），
      **未观测到成功完成的请求**，故"已修复"未由本轮证据签字。

## 可复用规则

判"某个 GUI 客户端在用哪条线路"，只认**它自己进程的外网连接目标**和**代理侧的转发行计数**；
判"线路能不能用"，只认**一次最小真实补全请求的状态码**。界面计时器和列表里的"正常"标签都不算证据。

## 适用范围与不适用范围

- 适用：任何自带服务商配置的桌面 AI 客户端 + 本地代理/路由切换器组合。
- 不适用：只读一份全局配置的 CLI（切全局路由即生效）。

## 剩余风险

大上下文（约 38 万 token 输入）请求在抖链路上更容易 502/超时，本轮未做同尺寸对照实测；
"服务模式装好后 TUN 是否稳定"未验证。
