# 踩坑：体检报"左右留白差 16px"，其实是位置和尺寸用了两套坐标系

> `verified`：2026-11-11 在窗口居中项目里用离屏窗口量化外延、修复后实测 L179 R179。

## 一句话结论

Windows 上同一个窗口有**两个矩形**：`GetWindowRect`（真实矩形，含不可见的阴影/边框外延）与
`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`（**可见框**）。
**拿真实矩形的坐标去配可见框的尺寸，算出来的"留白"必然一边少 8px、一边多 8px** ——
窗口其实是对称的，错的是这把两套坐标混着用的尺子。

## 触发条件与影响

- 项目或功能：窗口居中监视器 + 只读体检 `doctor.py` 的「最近 10 条落位记录」四边留白换算
- 环境与版本：Windows 11；工作区 2560×1540；红圈 2202×1340
- 触发条件：目标尺寸（可见框 2202×1340）+ 位置取「真实矩形」坐标（179−8=171）
- 影响范围：**只影响报表数字，不影响窗口实际落位**。危害是误判——
  看到 `留白 L171 R187` 会以为"没居中"，进而去改本来正确的缩放/居中代码。

## 复现步骤

1. 造一个离屏窗口（`-5000,-5000`），避开桌面干扰
2. 用 `SetWindowPos` 分 3 步移动，每一步立刻双读 `ext`（DWM 可见框）与 `real`（GetWindowRect）
3. 打印 `d_left = ext.left - real.left` 等四个差值
4. 用"真实坐标 + 可见尺寸"折算留白，观察左右是否相等

## 证据

```
ext = (-4992,-5000)-(-4208,-4408)      real = (-5000,-5000)-(-4200,-4400)
d_left=+8  d_top=0  d_right=8  d_bottom=8
每步 |real.left - last| = 0       每步 |ext.left - last| = 8
```

- 两个矩形**同步更新**（不存在"谁慢一拍"），只差一个恒定外延；
- 修复前后同一份日志的体检输出：
  - 修复前（老口径）：`目标位置(171,100)  留白(假) L171 R187 T100 B100`
  - 修复后：`目标位置(179,100)  留白 L179 R179 T100 B100`
- 真实应用同样成立：`ApplicationFrameHost.exe 1364x913 -> 2202x1340` 的外延也是 8px。

## 根因分析

- 已确认的根因：**同一份报表里"位置"和"尺寸"来自不同坐标系**。
  尺寸是可见框目标（`2202x1340`），位置却在动画日志里只记了「终点」＝真实矩形坐标。
- 排除过的假设：
  - "窗口真的偏了 16px"→ 否：`SetWindowPos` 收到的是换算后的真实坐标，可见框恰在 179；
  - "外延是非对称的、随窗口大小变"→ 否：离屏三步实测四个方向差值恒定。
- 问题归属：**日志口径**引入（动画行先写出来时只记了真实坐标）。

## 最小修复

1. 写日志时**两个坐标都记**，让读日志的人不必猜：

```python
log(f"{mode} {proc} {w}x{h}->{tw}x{th} 开始位移动画 3 帧 "
    f"起点=({start_x},{start_y}) 终点=({target_real_x},{target_real_y}) "
    f"可见目标=({tx},{ty})")          # ← 新增：可见框目标
```

2. 解析侧**优先用可见目标**；老日志（只有真实坐标）退回并显式标注"估算"，不冒充精确值：

```python
if vis:   point = (int(vis.group(1)), int(vis.group(2)))
elif anim: point, est = (..., ...), True      # 老日志：真实坐标
tail = "留白%s L%d R%d T%d B%d" % ("(估)" if est else "", ...)
```

## 可复用规则

1. **凡是要计算"边距/居中/对齐"的地方，位置与尺寸必须同源**：可见框配可见尺寸，真实矩形配真实尺寸。
2. 窗口类计算里，先把 `ext` 与 `real` 的差值量出来（本项目是 8px），再决定用哪一套；
   别假设"两个矩形一样"——Electron/Qt/UWP 的外延各不相同，UWP 走 `ApplicationFrameHost` 时更明显。
3. 报表里出现"巧合的小差值"（8px、16px 这种干净数字），优先怀疑**坐标系/单位**，而不是业务逻辑。
4. 老数据格式无法回溯时，宁可标"估算"，也不要给出看起来精确的错数字。

## 适用范围与不适用范围

- 适用：Windows 窗口几何、截图裁剪对齐、多显示器 DPI 换算、任何 ext/real 双矩形的场景。
- 不适用：无边框全屏窗口（两者相等，差值恒 0，混用也不出错——这正是它容易潜伏的原因）。

## 剩余风险

- 外延可能随 DPI 缩放变化（125% 下不一定仍是 8px）：本轮只在 100% 缩放下量化，
  换缩放后需重测，不能把 8 当成常量写死（代码里始终用运行时读到的差值换算，不硬编码）。
