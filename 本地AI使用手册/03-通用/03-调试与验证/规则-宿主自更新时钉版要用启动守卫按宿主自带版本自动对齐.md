# 规则：把"每次升级后人工重对齐"变成"启动时自动对齐"

> 上游事故与判据见 [[踩坑-钉死内核同名包版本遇宿主自更新即降级致启动fatal]]；
> 本条记的是**之后怎么让它不再复发**，含搭这套守卫时踩的两个真 bug。

## 一句话结论

钉版本身没错，错在它是**静态的**而宿主是**动态的**；解法是把"目标版本"的来源从人脑换成宿主自带的产物
（Electron 就读 `app.asar` 里的 `node_modules/*/package.json`），再挂一个**幂等且亚秒级**的启动守卫，
让每次启动先对齐、对齐不了才报警——而不是指望人记得。

## 结构（本机落位）

```
D:\DSH-Guard\
  dsh_kernel_sync.py     守卫本体（纯标准库；--check 只报告）
  start_dsh.bat          启动包装：跑守卫 → 再 start 真正的 exe
C:\Users\Admin\.dsh\guard\
  sync.log               每次启动一行，含"无需修复"也记
  pnpm-workspace.yaml.bak-<时间戳>   改盘前自动留档
  原快捷方式目标.txt      改写 .lnk 前的原 TARGET/ARGS/WORKDIR 留档
```

挂钩点（都回读过实际 TARGET）：
- 开始菜单 `Programs\DeepSeek Harness.lnk` → 改成指向 `start_dsh.bat`（**安装器下次可能重置它**）
- 桌面新建 `DeepSeek Harness（启动自动对齐）.lnk` → 指向同一个 bat（不依赖安装器，升级不会被覆盖）

## 守卫的判据来源（全部权威，不猜）

| 需要的值 | 从哪读 |
|---|---|
| 内核版本 | `app.asar` 内 `/package.json` 的 `version` |
| 每个被钉包的目标版本 | `app.asar` 内 `/dsh/node_modules/@deepseek-ai/<pkg>/package.json` 的 `version`，同名多份取**出现次数最多**的那个 |
| 该用哪个 pnpm | `resources/runtime/versions.json` 的 `pnpm`（内核自带版本；将来内核换大版本守卫自动跟上） |

asar 头解析（无需 asar CLI）：`pickle=uint32@4`、`jsonLen=uint32@12`、JSON 从偏移 16 起用
`raw_decode` 忽略尾部填充，**数据基址 = 8 + pickle**，再 `seek(base+offset)`。

## 两个必须做对的语义（我都踩过）

**1. 「profile 里没装这个包」是正常的，不是待修项。**
`@deepseek-ai/cordis` 在 profile 的 `node_modules` 里**从来就不存在**（由内核 asar 提供）。
我第一版把"没装"也判成不一致 ⇒ 守卫**每次启动都白跑一遍 `pnpm install`**，而且永远修不好。
正确语义：危险的是**「装了但是旧版」**（那才会遮蔽内核同名包）；缺席 = 正常。
→ 缺席的包只复核 YAML 值，不复核 `node_modules`。

**2. 只比 YAML 不够，必须再比 `node_modules` 实装。**
YAML 对 ≠ 装上了（安装中断、被人手改、锁文件回退都会造成"配置对、包旧"）。
只查 YAML 的守卫会自信地报「已对齐」，然后应用照样崩。
→ 两层都查；`node_modules` 里版本 ≠ 内核版本才列入修复。

## 退出码约定（包装器据此决定要不要拦）

| rc | 含义 | 包装器行为 |
|---|---|---|
| 0 | 本来就对齐 | 直接启动（实测 1.5 s 内） |
| 1 | 检测到漂移并已修好 | 提示一句后启动 |
| 2 | 需要修但失败 | **打印日志路径 + `pause`**，让用户看见再去修 |
| 3 | 需要修但应用开着（当前实现会自动结束它，见下） | — |

包装器**任何分支最后都会 `start` 主程序**（只有 rc=2 先 pause），避免"守卫坏了导致应用启动不了"这种单点故障。

## 复现与验证（不是"看起来对"，是造状态验）

```
# 造漂移：把 3 项 overrides 改回旧版并真装一遍，让 node_modules 也变旧
python - <<PY          # 见 03_工具脚本\wire_dsh_shortcuts.py 同目录的演练脚本
PY
python dsh_kernel_sync.py            # 期望 rc=1，日志列出 YAML 漂移 + 实装不符
python dsh_kernel_sync.py            # 再跑一次期望 rc=0（幂等，不重复安装）
```

实测记录（2026-11-04）：
- 快路径 **0.10 s**（`--check`），完整修复路径 **~1 s**（含 `pnpm install`，`Done in 639ms`）
- 演练一：`dsh-session 0.2.1-rc.5 / cosmokit 1.8.6` → 守卫识别 3 项 YAML 漂移 + 2 项实装不符 → 修好 rc=1
- 演练二：`dsh-llm / schemastery` 同样造旧 → rc=1，`[完成] 2 个包已对齐`
- 修好后经桌面 `.lnk` 启动：日志 `21:25:17 [OK] …无需修复`，应用 5 进程在跑，
  **crash 目录无新日志**（此前每次真崩都会留一份）
- 幂等复跑 rc=0，没有反复安装

## 可复用规则

1. **宿主会自更新 ⇒ 任何"对齐到宿主当前版本"的手工配置都必须自动化**，人记不住，机器能。
2. **目标版本要从宿主的产物里读**（asar / 内置 manifest / `versions.json`），不要写死在脚本里，
   也不要写死在配置里。
3. **守卫必须亚秒级快路径 + 幂等**：无事可做时 0.1 s 返回，别让用户为检查等 5 秒，也别每次触发安装。
4. **判"遮蔽"只看「装了且旧」**；"没装"通常是宿主自己提供，把它当故障会造成永久误修。
5. **挂钩要留一条不依赖安装器的入口**（自建的桌面快捷方式），因为安装器会重写它自己的 `.lnk`。
6. **改 `.lnk` 前把原 TARGET/ARGS/WORKDIR 落档**，出问题一眼能回退。

## 适用范围与不适用范围

- 适用：DSH / WorkBuddy / VS Code 扩展宿主等"宿主自带一套包 + 用户 profile 可覆盖依赖"的结构；
  一切用 `overrides`/`resolutions` 压制传递依赖的场景
- 不适用：宿主与依赖同源于同一构建产物、用户无法覆盖依赖的结构
- **已知覆盖不到的路径**：electron-updater 装完会**直接重启主 exe**，绕过包装器
  ⇒ 升级后的那一次自启仍可能崩一次；下一次从快捷方式启动就会被守卫修好。
  要连这一次也堵住，只有两条路（都需另行同意，本机未做）：
  ① 计划任务登录时跑守卫（属自启，用户原则是不给工具装自启）；
  ② IFEO `Debugger` 劫持该 exe 名（系统级、每次创建进程都过，但一旦守卫本身坏了应用就完全起不来）。

## 剩余风险

- 若某天内核把包从 `/dsh/node_modules/` 挪走，守卫会读不到目标版本 ⇒ 它按设计**只警告不动手**，
  需要人工更新路径常量（`ASAR` / `PROFILE`）。
- 守卫依赖 `D:\PyCharm\Python\python.exe`，bat 里有 `python` 兜底；两者都没了会退化成"直接启动不检查"。
- `dsh-agent-presets` 仍是 super-agent 带的 `0.1.2-rc.1`，不在钉版清单内，属同类隐患。
