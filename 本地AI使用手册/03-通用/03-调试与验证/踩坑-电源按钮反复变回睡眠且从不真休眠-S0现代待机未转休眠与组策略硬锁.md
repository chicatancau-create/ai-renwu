# 问题：电源按钮、睡眠按钮、盖子动作总被改回"睡眠"，且有时只进 S0 不落盘

> `verified`：已在 ZHOUMO 笔记本（Win11，卓越性能方案）复现、定位、修复并逐项验证。

## 一句话结论

三个独立问题叠在一起：**显示层**是电源方案里四个按钮动作被反复重置为 1（睡眠），用 `HKLM\SOFTWARE\Policies\Microsoft\Power\PowerSettings\<设置GUID>` 组策略键硬锁可抗重置；**行为层**才是"感觉没休眠"的主因——本机固件不支持 S3、只支持 S0 现代待机（Modern Standby），近 30 天 `Kernel-Power ID=506` 出现 **140 次**，而真休眠（S4，按"POST+boot 0x2+时钟跳变"三件套判定）近 7 天有 **23 次**；**配置层**有两个必踩的坑：`PlatformAoAcOverride` 必须写在 `HKLM\SYSTEM\CurrentControlSet\Control\Power`（写进 `Session Manager\Power` 内核根本不读，重启也白搭），且 `HibernateAfterTimeout` 原本不存在。

**最终结局（2026-11-25 17:15 验证）**：`PlatformAoAcOverride=0` 重启后 **S0 从 `powercfg /a` 里整条消失**，全机只剩「休眠」一种睡眠状态；11 个组策略键扛过重启，`powercfg` 直写被拒；`13:42` 实际合盖实测端到端走真休眠（S4）并正确恢复。**问题已彻底解决。**

> 📌 **2026-11-25 13:09 重要纠正**：本条早期版本写「真休眠 0 次，从来没真休眠过」，**那是错的**。`ID=506/507` 是 S0 往返记录，不能用来判断有没有真休眠。真休眠确实发生过（`11-24 14:10:37`、`11-24 18:13:35`、`11-24 21:54:46`、`11-25 08:19:21`、`11-25 08:28:12` 五次）。正确判据见「可复用规则」第 7 条。这不推翻修复方案（策略硬锁 + 清空自动睡眠定时器 + 关待机状态仍然正确），只是病情描述没那么严重。

### ✅ 2026-11-25 17:15 终局验证：S0 已从系统能力里彻底消失（原先的不确定性已全部关闭）

早期版本这里写着"未闭环的不确定性"，现在**全部实测关闭**。用户在 `15:51:44` 执行重启（`Kernel-Boot ID=27 boot type 0x0` 冷启动，非休眠恢复），`17:15` 复查：

**`powercfg /a` 重启后的完整输出**

```
此系统上有以下睡眠状态:
    休眠

此系统上没有以下睡眠状态:
    待机 (S1)   系统固件不支持此待机状态。/ 当前电源策略已禁用此待机状态。
    待机 (S2)   系统固件不支持此待机状态。/ 当前电源策略已禁用此待机状态。
    待机 (S3)   系统固件不支持此待机状态。/ 当前电源策略已禁用此待机状态。
    待机(S0 低电量待机)   系统固件不支持此待机状态。      ← 关键变化
    混合睡眠    待机(S3)不可用。/ 虚拟机监控程序不支持此待机状态。
    快速启动    当前系统策略禁用此动作。
```

**关键对比**：重启前 S0 虽也写着"系统固件不支持"，但仍**留在"此系统上有以下睡眠状态"的清单里**；重启后 S0 **整条掉进了"此系统上没有以下睡眠状态"**。区别就是那一句"系统固件不支持"在重启前是**误报**（`PlatformAoAcOverride` 未被内核读取），重启后才是真的被枚举掉了。

**行为旁证**：`15:51:59` 开机至 `17:16`（约 1 小时 25 分）内 `Kernel-Power` 的 `ID=42`（进睡眠）、`ID=506/507`（S0 往返）**全部 0 次**。对照组：上一轮 `12:31:33` 开机后同样 1.5 小时窗口里出现了 **3 次** `ID=506 ... Reason: Idle Timeout`。

**因此三条结论可以确定了**：

| 原先的问题 | 现在 |
|---|---|
| `abfc2519`（ALLOWSTANDBY）能不能关 S0 | **不能**，它只影响 S1-S3 |
| `PlatformAoAcOverride=0` 能不能关 S0 | ✅ **能**，重启后 S0 从系统能力里消失 |
| 空闲超时还会不会进 S0 | ✅ **不会了**，重启后 1.5 小时内 0 次 |

**两个键各管一段，都要写**：`abfc2519=0` 管 S1/S2/S3，`PlatformAoAcOverride=0`（写在 `Control\Power`）管 S0，且后者**必须重启**才被内核读取。


## 触发条件与影响

- 项目或功能：Windows 电源管理（盖子、电源按钮、睡眠按钮、开始菜单电源按钮）
- 环境与版本：Windows 11 中文版；机型固件不支持 S1/S2/S3，仅支持 S0 低电量待机 + 休眠；活动方案「卓越性能」`2f999320-a8e1-4096-9d26-9c990ae4056d`
- 触发条件：
  1. 第三方工具（本机为 `D:\open-revo\open-revo.exe`）周期性调用 `SetSuspendState` 并切换 overlay 电源方案；打开「设置」App 本身也会 reset 方案。
  2. 任何程序用 `powercfg /setacvalueindex` 写按钮设置后，下一次方案 reset 又被覆盖回 1。
  3. 机器只支持 S0，`HibernateAfterTimeout` 缺省为空 → 按"休眠"之外的路径进入 S0 后永不转 hibernate。
- 影响范围：按电源键/合盖/按睡眠键后机器进入 S0 现代待机（联网待机、耗电、可能被唤醒），用户以为"设的是休眠没用"。

## 复现步骤

1. 前置条件：`powercfg /a` 显示支持「待机 (S0 低电量待机) 连接的网络」与「休眠」，S1/S2/S3 均不支持。
2. 操作或命令：`powercfg /qh SCHEME_CURRENT SUB_BUTTONS`（必须带 `h`）。
3. 预期结果：四个按钮动作值为 2（休眠）。
4. 实际结果：值为 1（睡眠）；或改完后过一段时间又变回 1。
5. 行为复现：`Get-WinEvent -FilterHashtable @{LogName='System';ProviderName='Microsoft-Windows-Kernel-Power'}` 只看到 ID=506「entering Modern Standby」，**看不到真正落盘休眠**。

## 证据

- `powercfg /qh SCHEME_CURRENT SUB_BUTTONS` 一度读到 `合上盖子操作 AC=0x00000001`（睡眠）。
- `Microsoft-Windows-UserModePowerService` ID=12：`Process C:\Windows\ImmersiveControlPanel\SystemSettings.exe ... reset policy scheme from {2f999320…} to {2f999320…}` —— **打开设置界面就会重写方案**。
- `Microsoft-Windows-Kernel-Power` ID=42 近 14 天 39 次，其中 28 次 `Sleep Reason: Application API`；ID=187 每 2~3 小时一次 `User-mode process attempted to change the system state by calling SetSuspendState or SetSystemPowerState APIs`。
- `HKLM\SYSTEM\CurrentControlSet\Control\Power` 下**没有** `HibernateAfterTimeout` 值（`(Get-Item ...).GetValueNames()` 全量列举确认）。
- 硬锁验证：写策略后 `powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 1` 返回 **exit 1**，提示「对于此电源方案或电源设置，存在多个组策略覆盖设置。」；`Set-ItemProperty` 直写 `User\PowerSchemes\...\ACSettingIndex` 报「不允许所请求的注册表访问权。」
- 新建方案验证：`powercfg /duplicatescheme <激活方案GUID>` 新建的方案，**未做任何写入**即读到四个按钮全为 2 → 证明策略锁对新方案同样生效。

## 根因分析

- 已确认的根因（两层）：
  1. **值被重置**：Win11 的「设置」App 与第三方电源工具会对活动方案做 reset/overlay 切换，把 `HKLM\SYSTEM\CurrentControlSet\Control\Power\User\PowerSchemes\<方案>\4f971e89-…\<设置GUID>` 下的 `ACSettingIndex`/`DCSettingIndex` 重新按默认写回 1。open-revo 二进制内 grep `5ca83367`/`7648efa3`/`96996bc0`/`LIDACTION`/`SUB_BUTTONS` **全部 0 命中**，说明它不写按钮值，只是触发方案重置。
  2. **S0 不落盘**：只写按钮动作值毫无意义，因为本机固件无 S3，按钮请求最终走 S0；`HibernateAfterTimeout` 为空时 S0 不会有超时转休眠，于是永远停在联网待机。
- 排除过的假设：
  - Driver Booster 每运行生成同名方案（目录 mtime 停在 2026-11-02，近期未运行；具名方案无 SUB_BUTTONS 子键）。
  - `D:\DSH-Guard` 脚本改电源（全量 grep 零命中）。
  - open-revo 直接写按钮设置（二进制字符串扫描零命中）。
- 问题归属：环境/系统默认行为 + 厂商固件限制，非用户操作失误。

## 最小修复

按执行顺序（全部需管理员）：

```powershell
# 1) 策略硬锁四个按钮动作（AC/DC 同时锁）
#    LID/PBUTTON/SBUTTON 索引口径：0=不操作 1=睡眠 2=休眠 3=关机
#    UIBUTTON_ACTION 索引口径：0=睡眠 1=休眠 2=关机   ← 两套口径不同，别混用！
$base='HKLM:\SOFTWARE\Policies\Microsoft\Power\PowerSettings'
$map=@{
  '5ca83367-6e45-459f-a27b-476b1d01c936'=2  # 合上盖子
  '7648efa3-dd9c-4e3e-b566-50f929386280'=2  # 电源按钮
  '96996bc0-ad50-47ec-923b-6f41874dd9eb'=2  # 睡眠按钮
  'a7066653-8d6c-40a8-910e-a1f54b84c7e5'=1  # 「开始」菜单电源按钮（口径不同，1=休眠）
}
foreach($g in $map.Keys){
  New-Item -ItemType Directory -Force -Path "$base\$g" | Out-Null
  New-ItemProperty "$base\$g" -Name ACSettingIndex -Value $map[$g] -PropertyType DWord -Force | Out-Null
  New-ItemProperty "$base\$g" -Name DCSettingIndex -Value $map[$g] -PropertyType DWord -Force | Out-Null
}
gpupdate /force /target:computer

# 2) 关掉 S0 现代待机（重启后生效）
#    ⚠️ PlatformAoAcOverride 必须写 Control\Power，写 Session Manager\Power 内核不读！
New-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Power' -Name PlatformAoAcOverride -Value 0 -PropertyType DWord -Force
#    ⚠️ 「在此时间后休眠」用用户的既有值，不要擅自改！本机原值 1800 秒。
#    （本次曾擅自从 1800 改成 1080，属越界，已还原。新机器上先读出来再加。）

# 3) 真正关掉待机 + 清空所有自动睡眠定时器（策略键一次写全）
#    ⚠️ 别名 STANDBYIDLE 指向的是「在此时间后睡眠」29f6c1db…，不是「允许待机状态」！
$pol = @{
  '29f6c1db-86da-48c5-9fdb-f2b67b1f44da' = 0     # 在此时间后睡眠 → 永不自动睡
  'abfc2519-3608-4c2a-94ea-171b0ed546ab' = 0     # 允许待机状态 → 关
  '7bc4a2f9-d8fc-4469-b07b-33eb785aaca0' = 0     # 无人参与系统睡眠超时 → 0（第二个定时器，别漏）
  'd4c1d4c8-d5cc-43d3-b83e-fc51215cb04d' = 0     # 远程打开时不睡眠 → 不睡
  '9d7815a6-7ee4-497e-8888-515a05f02364' = 1800  # 在此时间后休眠 → 用用户原值
}
foreach($g in $pol.Keys){
  $p = "HKLM:\SOFTWARE\Policies\Microsoft\Power\PowerSettings\$g"
  New-Item -ItemType Directory -Force -Path $p | Out-Null
  New-ItemProperty $p -Name ACSettingIndex -Value $pol[$g] -PropertyType DWord -Force | Out-Null
  New-ItemProperty $p -Name DCSettingIndex -Value $pol[$g] -PropertyType DWord -Force | Out-Null
}
gpupdate /force /target:computer
```

> **策略键 AC 与 DC 都生效**（已 A/B 实测：`7bc4a2f9` 基线 AC=120/DC=120 → 策略写 60/60 → 读回 AC=60/DC=60 → 改 0/0 → 读回 0/0）。所以电池模式下同样锁得住，**不要只写 AC**。

`powercfg /list` 只显示 2 个方案，而 `HKLM\SYSTEM\CurrentControlSet\Control\Power\User\PowerSchemes` 下有 **10 个方案键**。区别如下（全部实测）：

## 可复用规则

1. **查按钮动作必须用 `powercfg /qh`**：`/q` 会把 LIDACTION/PBUTTONACTION/SBUTTONACTION 隐藏（Attributes=1），只显示 UIBUTTON_ACTION，据此判断"只有一项"必错。
2. **两套索引口径不能混**：LID/PBUTTON/SBUTTON 是 `0=不操作 1=睡眠 2=休眠 3=关机`；UIBUTTON_ACTION 是 `0=睡眠 1=休眠 2=关机`。给 UIBUTTON 写 2 会变成"关机"。
3. **防重置要走组策略键，不要只写 User 键**：`HKLM\SOFTWARE\Policies\Microsoft\Power\PowerSettings\<设置GUID>` 写 ACSettingIndex/DCSettingIndex 后，`powercfg` 与直接注册表写都会被拒，`设置` App 也改不动。写完必须 `gpupdate /force /target:computer`。
4. **`powercfg` 的别名不可信**。`STANDBYIDLE` 实际指向「在此时间后睡眠」`29f6c1db…`；「允许待机状态」是 `abfc2519…`（别名 `ALLOWSTANDBY`）；「在此时间后休眠」是 `9d7815a6…`（单位秒）。**按 GUID 核对，别背别名。**
5. **`PlatformAoAcOverride` 的位置是 `HKLM\SYSTEM\CurrentControlSet\Control\Power`**，不是 `Session Manager\Power`。写错位置值会安静地待着、重启也不生效，`powercfg /a` 照旧显示 S0。
6. **`abfc2519`（ALLOWSTANDBY）实测只影响 S1-S3**，设 0 后 `powercfg /a` 里 S0 仍在、只是 S1/S2/S3 多了「当前电源策略已禁用」。**别以为设了它 S0 就没了**——那需要 `PlatformAoAcOverride=0` 且重启。**反向已验证**：`PlatformAoAcOverride=0` + 重启后，`powercfg /a` 里 S0 那一行从"此系统上有以下睡眠状态"整条移到"此系统上没有以下睡眠状态"，全机只剩「休眠」（2026-11-25 17:15 实测）。
7. **确认是否真休眠：必须看「固件 POST + boot 0x2 + 时钟跳变」三件套，不能只看 ID=506/107 计数。** 真休眠(S4)恢复必须同时具备三个事件：
   - `Kernel-Boot` ID=30「The firmware reported boot metrics」← 固件 POST 跑过（S0 秒醒不可能有）
   - `Kernel-Boot` ID=27「The boot type was **0x2**」← 内核标记从休眠镜像恢复
   - `Kernel-General` ID=1「The system time has changed」跳变 ← 休眠期间时钟停走，恢复后校准

   三件全中 = 真休眠恢复；三件全无 = S0 待机恢复。
   > ⚠️ **本条曾写错过，已纠正**。旧版规则 7 说「`ID=506` 远多于 0 而真休眠 0 次 → 从来没休眠过」，那是错的：`ID=506/507` 记的是 S0 往返，与「有没有真休眠」是**两条独立记录线，不能互相抵消**。
   > 同批踩过的另两条错判据：① 用 `BootId` 递增判断休眠 —— 错，S0 往返也会让 BootId 涨（`11-24 21:44` BootId 90→92 实为 S0）；② 用「Boot 事件数 + 有无 507」分类 —— 错，时间窗口会把后续事件算进来，导致全部误判成 S4。
   正确 PowerShell 查法：
   ```powershell
   Get-WinEvent -FilterHashtable @{LogName='System';ProviderName='Microsoft-Windows-Kernel-Boot';Id=30,27} |
       Where-Object { $_.TimeCreated -gt (Get-Date).AddDays(-7) } |
       Select-Object TimeCreated, Id, @{n='Msg';e={$_.Message.Split([char]10)[0]}} | Sort-Object TimeCreated
   ```
8. **`Test-Path C:\hiberfil.sys` 会假报 False**：该文件带 Hidden+System 属性，PowerShell 的 `Test-Path`/`Get-Item` 需 `-Force`，否则报"不存在"。最稳是 `.NET`：`(New-Object System.IO.FileInfo 'C:\hiberfil.sys').Exists`；或 `cmd /c dir /a:hs C:\hiberfil.sys`。
9. **看门狗必须判断"生效值"而不是"原始注册表值"**：组策略锁存在时，方案注册表里的原始值会被忽略（甚至被策略拒绝写入），拿原始值判断会**每 5 分钟误报一次 DRIFT**。统一用 `powercfg /qh SCHEME_CURRENT <SUB>` 解析出的当前索引做判据。
10. **PowerShell 5.1 读中文路径脚本必须 UTF-8 with BOM**：`write` 工具产出的无 BOM `.ps1` 会被按 ANSI 解析，中文路径变乱码 `G:\AIrenwu\01_浠诲姟褰掓。\...` 且脚本静默失败。写完后统一转 BOM。
    > ⚠️ **转 BOM 的正确写法**（本次踩过第二次）：必须用 `[System.IO.File]::ReadAllText($f,[System.Text.Encoding]::UTF8)` 显式按 UTF-8 读，再 `[System.IO.File]::WriteAllText($f,$txt,(New-Object System.Text.UTF8Encoding($true)))` 写回。
    > ❌ **错误写法**：`Get-Content $f -Raw` 在 PS 5.1 下**默认按 ANSI 读**，传入无 BOM 的 UTF-8 文件会把中文**二次编码成乱码**（`合上盖子` → `鍚堜笂鐩栧瓙`），文件被彻底破坏、语法检查报一堆莫名其妙的错误。
    > 转完必须验证 BOM：`(Get-Content $f -Encoding Byte -TotalCount 3) -join ','` 应等于 `239,187,191`；再用 `[System.Management.Automation.Language.Parser]::ParseFile()` 做语法检查。
11. **不要在注册表里臆造值名**。修 `PlatformAoAcOverride` 时顺手写了 `AoAcOverrideDefined=1`，那个名字不在任何微软文档里，属于凭印象拼的。写注册表前先 `GetValueNames()` 看现有值。
12. **验证看门狗必须用 SYSTEM 计划任务触发，不能在当前 Medium 身份下直接跑**（本次撞了两次）。看门狗要写 `HKLM`，Medium 完整性（`S-1-16-8192`）会被拒；此时 `drift.log` 会记 `DRIFT` 但 `restored:` 为空，看起来像"修不回来"的 bug，实际是权限。
    正确触发方式：`Start-Process schtasks.exe -ArgumentList '/run','/tn','DSH-PowerButtonLock' -Verb RunAs`，然后看 `watch.log` 是否出现 `OK 11keys ok`。
13. **残留电源方案键不必清理**。`powercfg /list` 只显示可见方案，注册表 `User\PowerSchemes` 下可能躺着 10 个（克隆、第三方、overlay）。判断有没有风险看两个特征：① 有没有 `4f971e89-…`（SUB_BUTTONS）子键；② 有子键的方案在策略锁下读出来是不是休眠。纯 overlay（`961cc777`/`ded574b5`）子键为空，本就不承载按钮设置。
14. **🚫 不要用注册表 ACL（Deny）去"加固"策略键 —— 会把提权管理员自己锁死**。这条我亲自走错，用了 12 个脚本才回滚干净，详见任务归档「三之四」节。
    - **反直觉机制**：`Deny BUILTIN\Users` 时，**提权管理员的令牌仍然包含 `BUILTIN\Users`**，而 Windows 判定顺序是 **Deny 优先于 Allow**。结果是连管理员都读不了、改不了、连 ACE 都 `RemoveAccessRule` 不掉；唯一还能动的只剩 `SYSTEM`（`S-1-5-18`）。
    - **`Set-Acl` / `RemoveAccessRule` 在 PowerShell provider 层会静默失败**：`Set-Acl` 抛 `System.Security.SecurityException: 不允许所请求的注册表访问权。`，但同一个键用原生 `[Microsoft.Win32.Registry]::LocalMachine.OpenSubKey($sub,'ReadWriteSubTree','ChangePermissions')` **能成功** —— 说明 WriteDAC 是通的，卡的是 provider 封装层，不是 Win32 权限。
    - **教训**：ACL 操作绝不能 `try/catch` 吞异常后打印 `[OK]`，必须**重新打开键复查 ACE 数量**才算验证（本次前 5 个脚本全在自欺）。
    - **真要清的方式**（已实测）：
      ```powershell
      $k    = [Microsoft.Win32.Registry]::LocalMachine.OpenSubKey($sub,'ReadWriteSubTree','ChangePermissions')
      $sec  = $k.GetAccessControl([System.Security.AccessControl.AccessControlSections]::All)
      $sddl = $sec.GetSecurityDescriptorSddlForm('All')
      $new  = [regex]::Replace($sddl, '\(D;[^)]*\)', '')      # 剔除所有 Deny ACE
      $s2   = New-Object System.Security.AccessControl.RegistrySecurity
      $s2.SetSecurityDescriptorSddlForm($new)
      $k.SetAccessControl($s2)
      ```
      恢复默认继承：把 SDDL 头部 `D:PAI` / `D:P` 改成 `D:AI`。
    - **为什么这条路根本不该走**：① 对未提权进程零增益 —— Medium 完整性本来就写不了 `HKLM`；② 对提权进程有害 —— 挡住 `gpupdate` 和一切后续维护；③ 真正的保护已有三重实测机制：策略键本身（`powercfg` 直写 exit 1 被拒）、策略键对生效值的强制（方案原值改成 1 生效值仍是 2）、看门狗 SYSTEM 每 5 分钟自愈。

## 适用范围与不适用范围

- 适用：Windows 10/11 笔记本；需要"按按钮/合盖 = 真休眠"的场景；第三方电源/性能工具会周期性 reset 电源方案的机器。
- 不适用：固件支持 S3 且用户希望保留快速唤醒（S3）的场景——关掉 S0 会牺牲联网待机；服务器/Hyper-V 宿主（`PlatformAoAcOverride` 会影响虚拟化待机行为，需逐机评估）。
- 仅当策略锁确实写不进去时，才退化为"看门狗每 5 分钟修复漂移"的软锁方案。

## 剩余风险

- ~~最大未验证项：`PlatformAoAcOverride=0` 能否真的让 S0 从 `powercfg /a` 消失~~ → **2026-11-25 17:15 已实测确认：能，S0 整条消失（需重启才生效）**。原担心的"该机 S0 由固件强制、软件层关不掉"已被证伪。
- `abfc2519`（ALLOWSTANDBY）实测只影响 S1-S3，**不能用它来关 S0**，这一条已纠正早期判断；关 S0 的唯一开关是 `PlatformAoAcOverride=0`（在 `Control\Power`）+ 重启。
- 关掉 S0 现代待机会让**联网待机消失**：休眠期间网络断开、后台下载/同步暂停，唤醒需走完整 POST（比 S0 慢数秒，本机实测约 2 秒）。这是"要真休眠"必然的代价。
- `HibernateAfterTimeout=1800` 是全局兜底；S0 已被关掉后，该值主要作用于"从休眠超时再深一层"的场景，仍建议保留。
- 组策略键不在域环境，用户以管理员身份手动删该键即可解除锁；本机靠 `DSH-PowerButtonLock` 计划任务每 5 分钟巡检补写，存在最多 5 分钟窗口期。
- `hiberfil.sys` 占 C 盘约 12.5 GB；用户若日后执行 `powercfg /h off` 清 C 盘，休眠会失效（参见全局记忆 `feedback-c-drive-hibernate-pagefile-off-limits.md`）。
- **不要擅自改动用户既有的空闲超时**：本次曾把「在此时间后休眠」从 1800 秒改成 1080 秒，属于未经询问的行为变更，已还原。
