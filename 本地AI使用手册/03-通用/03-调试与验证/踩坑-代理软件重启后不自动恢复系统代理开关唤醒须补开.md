# 问题：代理软件重启后不自动恢复系统代理开关，唤醒须显式补开并等端口

## 一句话结论

"关代理软件前先关系统代理"的逆向不自动成立：FlClash 重启后不会自己把 `ProxyEnable` 开回来。收尾若关了系统代理，唤醒必须显式补开，且要等代理端口真正可连通再开；是否补开取决于"收尾前是否开着"。

## 触发条件与影响

- 项目或功能：`session_end.py` 休眠收尾关代理 → 唤醒重启 FlClash
- 环境与版本：Python 3.14；Win11；FlClash；系统代理 `127.0.0.1:7890`
- 触发条件：收尾把 `ProxyEnable` 关成 0 并退出 FlClash；唤醒重启 FlClash。
- 影响范围：FlClash 在跑但 `ProxyEnable` 仍 0，全机走直连，需代理的站点全灭。

## 复现步骤

1. 前置条件：FlClash 在跑、`ProxyEnable=1`。
2. 操作或命令：`_do_shutdown`（关代理 + 退 FlClash）→ `_do_resume`（重启 FlClash）。
3. 预期结果：唤醒后代理恢复。
4. 实际结果：FlClash 重启了，但 `ProxyEnable` 仍 0。

## 证据

- 真机完整闭环 `tmp\_verify_full_cycle.py`：收尾后 `ProxyEnable=0` + 两进程死；`_do_resume` 重启 FlClash 52404 + core 8248，但 `ProxyEnable` 仍 =0。
- 修复后 `tmp\_verify_g3.py`：`_do_resume` 重启 FlClash 46732 + core 50488，`ProxyEnable` 自动回 1（G3 自己开的，非兜底）。

## 根因分析

- 已确认的根因：FlClash 重启后不自动恢复系统代理开关（`ProxyEnable` 是全局注册表值，无进程维护，FlClash 启动不写回）。
- 排除过的假设：不是"FlClash 没起来"——进程在跑、端口在听，只是开关没开。
- 问题归属：修改前已有（旧实现唤醒只重启进程，不管代理开关）。

## 最小修复

`_do_shutdown` 记 `proxy_was_on=bool(ok and was_on)`（只有真关掉了且此前开着才记）。`_restart_apps` 末尾若 `proxy_was_on` 则 `_restore_proxy`：等目标进程出现(≤5s) → `_wait_proxy_listening`（读 `ProxyServer` 端口，socket 连 `127.0.0.1:port`，≤6s）→ `enable_system_proxy`（写 `ProxyEnable=1` + wininet InternetSetOption 通知）→ 复位 `proxy_was_on`。判不出端口/超时则退回固定 `sleep 1.5s` 再开（不劣于旧行为）。

## 可复用规则

收尾若关了系统代理，唤醒/恢复时必须显式补开，不能假设代理软件重启会自己开回来。补开前等代理端口真正可连通（socket 连一次），别盲等固定时长；判不出端口就退回固定等待兜底。是否补开取决于"收尾前是否开着"（`proxy_was_on`），别把用户本就关着的代理强行打开。改 `ProxyEnable` 后要 wininet 通知，否则已开着的程序不重读。

## 适用范围与不适用范围

- 适用：任何"关代理软件 + 关系统代理"的收尾，其唤醒/恢复侧。
- 不适用：TUN/虚拟网卡模式（不依赖 ProxyEnable）；PAC 模式（清 AutoConfigURL 而非 ProxyEnable）。

## 剩余风险

FlClash 版本/配置变化可能改变"重启后是否自动开代理"的行为；端口等待上限 6s，极慢启动可能仍提前开（有固定兜底）。新代码未经历真实过夜休眠。
