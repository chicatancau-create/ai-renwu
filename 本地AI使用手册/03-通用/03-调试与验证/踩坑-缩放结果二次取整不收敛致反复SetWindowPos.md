# 踩坑：等比缩放结果"再算一次会变"，1px 漂移让轮询反复调整窗口

> `verified`：2026-10-19 在窗口居中项目里实测复现与修复；影响被 `tolerance_px=3` 吸收，
> 属"不致命但会做无用功"，具体影响边界见「证据」。

## 一句话结论

宽度、高度**各自** `round()` 时，取整误差会让"把结果再喂回去算一次"得到不同的尺寸
（1682×1294 → 1681×1294）。轮询型程序若用"是否等于目标"判断收敛，就会出现反复 SetWindowPos。
修法：**先定受约束更紧的那条主轴并取整，另一边由比例反算**，使 `round(目标)` 再算仍是自身。

## 触发条件与影响

- 项目或功能：窗口居中常驻监视器（200ms 轮询 + 4s 宽限期）
- 环境与版本：Python 3.14；工作区 2560×1540；`shrink_h_to=0.84` → 高上限 1293.6（带小数）
- 触发条件：缩放的"高"恰好卡在上限（1293.6），宽按 f 算出来落在 x.5 附近
- 影响范围：宽限期内多做几次 SetWindowPos、多打几行日志；**不会**造成无限循环
  （判定侧 `tolerance_px=3` 吸收了 1px）

## 复现步骤

1. 输入 1300×1000，框 (1920, 1293.6)
2. 第一次：f = 1.2936 → w = 1681.68→**1682**，h = 1293.6→**1294**
3. 把 1682×1294 再当输入算一次：f' = 1293.6/1294 = 0.99969 → w = **1681**
4. 预期：同一尺寸重复计算结果不变；实际：差 1px

## 证据

```
1300x900  -> 1869x1294 -> 再判 1868x1294
1300x1000 -> 1682x1294 -> 再判 1681x1294
1400x1000 -> 1811x1294 -> 再判 1810x1294
批量扫描 20 组尺寸：8 组出现漂移（全部是"高卡上限"的组）
判定侧 tolerance_px = 3  → 1px 差值被判为"已就位"，故不反复
```

## 根因分析

- 已确认的根因：两次独立 `round()` 破坏了"同尺寸 → 同结果"的幂等性；
  而轮询程序天然会"拿当前结果再算一次"，于是把浮点误差放大了。
- 排除过的假设：
  - "是窗口被程序自己改回去"→ 否：纯函数输入输出即可复现，与窗口无关。
  - "是 DPI 缩放"→ 否：全程 DPI-aware，坐标一致。
- 问题归属：**本次修改引入**（新缩放规则引入了带小数的上限）。

## 最小修复

```python
def fit_by_box(w, h, box_w, box_h):
    f_w, f_h = box_w / w, box_h / h
    if f_w <= f_h:                       # 宽是约束更紧的一边：定宽、反算高
        nw = max(1, round(w * f_w))
        nh = max(1, round(h * (nw / w)))
    else:                                # 高是约束更紧的一边：定高、反算宽
        nh = max(1, round(h * f_h))
        nw = max(1, round(w * (nh / h)))
    return nw, nh
```

修复后同一尺寸重复计算 8 组全部稳定（漂移 0 例）。

## 可复用规则

1. 任何"把结果再喂一遍"会被调用的纯函数（轮询、增量同步、幂等接口），
   **必须自测 `f(f(x)) == f(x)`**，至少对尺寸/坐标类结果。
2. 等比缩放不要两边各 round：**定主轴 + 反算另一边**。
3. 还要识别"到底靠什么收敛"：本例真正兜住的是 `tolerance_px`，
   但**不能把容差当设计**——容差是安全网，不是正确性。

## 适用范围与不适用范围

- 适用：窗口/控件尺寸计算、UI 布局取整、图片缩放、实时轮询的目标值计算。
- 不适用：一次性计算、结果不被回读的场合（漂移无实际影响）。

## 剩余风险

主轴选择依赖 `f_w <= f_h` 的比较，若框宽高相同需明确取哪一侧（本例取宽，结果对称）：
未覆盖"两轴完全相等且原比例非整数"的极端情形。
