# 问题：插件接管了宿主方法后，点一下就永久卡在「切换中…」，日志只有一行 `ENTER` 然后彻底静止

## 一句话结论

被包装的内核方法**第一件事就是 `await` 一张「串行化表」里的 Promise**（`this.switches.get(id) ?? Promise.resolve()`）。
包装者为了「延续串行化」把自己的任务也写进了同一张表，再去调用内核方法——
内核于是 await 包装者那个**还没结束**的任务，包装者又在等内核返回，形成环。
**表现极具迷惑性：没有任何报错、没有超时、没有堆栈，日志停在入口那一行，界面永远转圈。**

## 触发条件与影响

- 项目或功能：DSH `desktop` profile 的 `dsh-preset-unlock` 插件，包装 `agentPresets.select`
- 触发条件：**会话已经跑过至少一轮**（`boundary.lastTurn > 0`），此时内核会走 `switches` 串行化分支
- 影响：整个「切换模式」功能永久卡死，且用户看到的是「正在切换」而非「失败」，不会自己恢复

## 复现步骤

1. 插件包装 `select`，为「防止并发交错」延续内核的串行化：

   ```js
   const previous = this.switches.get(agent.id) ?? Promise.resolve()
   const task = previous.then(async () => {
     return await downstreamSelect.call(this, agent, agentPreset)  // ← 死在这里
   })
   this.switches.set(agent.id, task)   // ← 致命：自己的任务进了内核的表
   return await task
   ```

2. 内核 `select` 的源码（从 `app.asar` 取出，逐字）：

   ```js
   async select(agent, agentPreset) {
     const turn = (this.switches.get(agent.id) ?? Promise.resolve()).then(async () => {
       /* 边界检查 → recompose → append */
     })
     const guard = turn.catch(() => void 0)
     this.switches.set(agent.id, guard)
     try { return await turn } finally { /* 清理 */ }
   }
   ```

3. 预期：切换完成
4. 实际：界面永远「切换中…」；插件日志只有 `ENTER:`，之后再无任何行

## 证据（本轮实测）

死锁现场日志，两条真实点击后**再无任何输出**：

```
09:00:29  v6 ENTER: agentPreset=solo agentId=session-409eafde-... hasCtx=true
09:01:05  v6 ENTER: agentPreset=solo agentId=session-409eafde-... hasCtx=true
（之后彻底静止，无 PASS / WAIT / REFUSE / 异常）
```

对照同一版本在**会话未开始**时的正常路径，日志是完整的：

```
v6 ENTER → v6 PASS: 内核直接通过，返回 preset-team
```

差别就在：会话未开始时 `switches` 是空的，`await Promise.resolve()` 立即通过，环不存在。

修好后同一场景：`elapsed=2ms`（此前是永不返回）。

## 根因分析

内核把 `this.switches` 当作**跨调用的串行化链**，其语义是「同一会话的切换排队执行」。
包装者想延续这个语义，但忽略了**内核方法自己也会读写这张表**：

```
包装者 task ──await──> 内核 select ──await──> switches.get(id)
     ↑                                              │
     └──────────── 包装者把自己的 task 放在了这里 ←──┘
```

这不是「偶尔卡一下」，而是**必然的循环等待**：只要包装者先写表、再调内核，就一定死锁。

## 修复

**用自己的队列，与内核的 `switches` 完全隔离**，并在调用内核前清掉可能残留的历史死链：

```js
const QUEUE = Symbol.for('dsh.preset-unlock.queue')   // 自己的表，不碰 this.switches
const queue = this[QUEUE] instanceof Map ? this[QUEUE] : new Map()
const previous = queue.get(agent.id) ?? Promise.resolve()

const run = async () => {
  // 清残留：历史上死锁留下的链永不 settle，会让之后每次调用都被拖住
  if (this.switches instanceof Map && this.switches.has(agent.id)) {
    this.switches.delete(agent.id)
  }
  const direct = await downstreamSelect.call(this, agent, agentPreset)   // 内核的表此刻是干净的
  ...
}

const task = previous.then(run)
const guard = task.catch(() => undefined)
queue.set(agent.id, guard)
try { return await Promise.race([task, timeout]) }
finally { if (queue.get(agent.id) === guard) queue.delete(agent.id) }
```

三个要点，缺一不可：

1. **绝不把自己的任务写进被包装对象的串行化表**——那张表是内核私有的，包装者只读不写；
2. **调内核前清掉本会话的残留链**——否则一次历史死锁会永久污染后续所有调用（这次就是踩到 v6 留下的死链）；
3. **加兜底超时 + 客户端独立超时**——任何未来的等待环都不能让界面永远转圈。宿主 `200s`、客户端 `215s`，客户端比宿主长，正常路径永远由宿主先返回。

## 排查这类「卡死且无日志」的方法

按这个顺序，比读代码快：

1. **看日志停在哪个标记**。入口有 `ENTER`、后续无任何行 ⇒ 卡在「入口之后、第一个 await 返回之前」，不可能是业务逻辑错。
2. **对照一次成功路径的日志**。同版本在另一种前置条件下能走完 ⇒ 差别就在那个条件（这里是「会话是否已开始」）。
3. **把被包装方法的真实源码取出来读**，别凭印象。Electron 的 `app.asar` 可直接按头解析取文件，不需要 asar CLI（见另一条记录）。
4. **重点找 `await` 同一张表/锁/信号量**。串行化、限流、去重表是死锁高发区。
5. **写一个「内核语义与真身一致」的假内核来复现**。本条的回归测试就是让假 `select` 也去 `await switches`，不修就 5 秒挂死、修了 2ms 通过——比在真实环境里反复点可靠得多。

## 判据纪律

- **「没报错」不等于「在正常工作」**。这次是 Promise 永久 pending，JS 层面完全静默；判据必须是「有超时 + 有明确错误信息」，不能靠「看起来在转圈」。
- **兜底超时是功能的一部分，不是保险**。任何跨进程调用都必须能在有限时间内给出确定结果，否则用户无法区分「慢」和「死了」。
- 回归测试要能**区分死锁和慢**：用 `Promise.race` + deadline，断言「N 秒内返回」，而不是只断言最终值。
