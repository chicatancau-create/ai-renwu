# 问题：手写无 schema 的 protobuf 解析器，文本被当成子消息吞掉；只认一个容器字段号又丢了 105 条

> 来自一个已完成并归档的即时通讯群采集工程（原目录已删除，代码在私有仓库）。
> 结论与平台无关，任何「只有抓包、没有 .proto」的报文逆向都适用。

## 一句话结论

**UTF-8 中文正文按字节看是一段合法的 protobuf wire**，先递归解析子消息就会把正文吃掉，
只剩十六进制或空串——判定顺序必须是**文本优先、子消息其次**，并用控制字节比例把二进制段拒掉。
另一头，**「这是一条消息」不能靠容器字段号识别**：同一接口至少有两个容器（实测 `301` 与 `2043`）挂着消息体，
只认其中一个会静默丢数据（实测丢 105 条，占当日样本 36%），且不报错、日志全绿。

## 触发条件与影响

- 项目或功能：抓取 IM 长连接/HTTP 兜底接口的响应体，无 `.proto`，只有抓包得到的 base64/hex 报文
- 环境与版本：Python 3.11 纯标准库自研解码器；无 protobuf 运行时依赖
- 触发条件：把「字段是嵌套 message」放在「字段是文本」之前判定；或用固定容器号白名单挑消息
- 影响范围：**数据静默缺失**，条数偏少但全流程无异常。第一次交付只报出 3 条，被用户当场质疑「怎么可能只有三条」，
  回头才发现两个独立缺陷（容器漏判 + 文本被吞）叠加

## 复现步骤

1. 前置条件：一条只含中文文本的消息体（无附件、无卡片）
2. 操作或命令：
   ```python
   # 缺陷一：递归优先
   def walk(fields):
       for f in fields:
           if is_bytes(f): yield from walk(parse(f.value))   # 正文走这条分支被吞
           elif is_text(f): yield f.value
   # 缺陷二：容器白名单
   MSG = (301,)   # 实测 2043 也挂消息，且是初始化响应里的主要载体
   ```
3. 预期结果：正文可读；当日消息全量入库
4. 实际结果：正文段解析出「结构合法但内容是乱码的字段树」，可读文本数从 247 掉到 0；
   当日条数 288 → 183（少 105），`今日样本 166` 与实际 `67` 两处口径互相矛盾

## 证据

**同一份报文，三种判定顺序的结果（实测）**

```
递归优先      : 可解码文本 0 条，正文列显示成 hex（如 e6b689e59cb0…）
文本优先      : 可解码文本 247 / 288 条（41 条是图片/卡片等非文本，本就没有正文）
文本优先+控制字节闸门: 同上，且 hex 退化列 0 条
```

**容器分布（按报文实测计数）**

```
container 301  → 183 条   ← 第一版只认这个
container 2043 → 105 条   ← 漏掉的就是这批
合计           → 288 条
```

**字段号语义不能靠猜，要靠 distinct 统计（实测）**

```
field 1 / 5  → 会话 ID（两处同值，19 位十进制）
field 3      → 服务端消息 ID（单调，用作去重键）
field 7      → 发送者（21 个不同值 = 群里 21 人，对得上）
field 10     → 毫秒墙钟（落在当日区间）
field 14     → 作者 sec_uid
field 4 / 13 → 1.67e15 量级排序值，**不是时间**（当时间用会把消息排到 5 万年后）
```

**19 位纯数字 ID 被通用文本规则降级（实测）**

```
规则「len>=24 才算文本」→ 会话 ID 长 19 位 → 不达标 → 显示成 hex 串
改法：纯 ASCII 数字单独成一支，判为文本
```

**取证通道自身会丢数据（实测）**

```
CDP Network.responseBody() 打在长轮询接口上 → 无界阻塞，整轮探针挂死
无界 gather 读并发响应体 → 已捕获 406 条响应随异常一起丢弃
改法：wait_for(8s) 单个体超时 + 有界 drain + 异常路径先保留已取记录再抛出
```

## 根因分析

- 已确认的根因：
  1. protobuf 的 wire 格式对任意字节序列都宽容，文本被误判为嵌套结构是**设计使然**，不是解析器 bug；
     只有把「可读文本」放在判定链第一位，才能压住这个默认倾向。
  2. 容器字段号是接口版本演进的产物，同一接口多容器并存；任何「按号挑消息」都是白名单，漏一个就少一批。
  3. 长轮询/流式接口上，「读响应体」是需要超时的操作，不是瞬时操作。
- 排除过的假设：
  - 不是分页不足：游标翻到最早一页仍是 183 条，缺的 105 条从未出现在请求里。
  - 不是编码问题：同一字节段 `errors="replace"` 解码正常，问题在判定顺序。
  - 不是平台「不提供历史」：改判界后当日 288 条全部拿到，只是不能声称跨过了 00:00。
- 问题归属：本次解码器设计引入，非外部服务故障。

## 最小修复

1. 解码器判定顺序固定为：**标量文本 → 控制字节闸门 → 数字/布尔 → 才递归子消息**；
   文本支要求可打印比例，含控制字节即拒。
2. 消息判界改成**特征组合**，三件齐备才算一条消息：稳定 ID + 毫秒墙钟 + 至少一个可解码内容段。
   新增容器号不需要改代码，因为判据不看容器。
3. 语义字段用 distinct 统计反查，不做假设；疑似时间戳要验证量级与当日区间，验证不过的一律不入时间列。
4. 采集通道：每个响应体读取带超时，并发有界，异常路径保留已捕获数据。

## 可复用规则

- 拿到无 schema 报文，**先统计字段号的 distinct 值与量级，再决定语义**；对「看起来像时间」的数字先验区间。
- 任何「按字段号/容器号挑数据」的实现，都要用**全量报文按容器分组计数**做一次对照，差值不为 0 就是漏判。
- 交付前的自检项：可读文本条数 / 总条数 这个比值如果异常低，第一嫌疑是判定顺序把正文吞了，不是数据本身没文本。
- 长轮询接口上的「取响应体」必须带超时，且超时不能整批丢弃已取数据。
- 单次经验不覆盖的例外：若目标接口有官方 `.proto` 或 SDK，直接用 schema，别手写解码器。

## 适用范围与不适用范围

- 适用：只有抓包、无 schema 的 protobuf/自定义二进制报文解码；无头浏览器 CDP 取证通道设计
- 不适用：有官方 schema 的场景；JSON/表单类接口；不经过响应体的纯 UI 取证

## 剩余风险

- 平台改版后特征字段（ID/墙钟/内容段）若同时改名或换语义，判界会整体失效且不报错，需要保留「按容器分组计数」这条自检。
- 「不漏消息」仍未取得跨 00:00 的分页证据，本记录只保证当日抓到的部分可解码。
