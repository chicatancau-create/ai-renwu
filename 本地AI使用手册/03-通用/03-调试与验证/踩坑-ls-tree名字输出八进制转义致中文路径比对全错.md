# 问题：用 `git ls-tree --name-only` 拿远端提交的文件清单和本地目录做哈希比对，结果「0 个相同」

## 一句话结论

`git ls-tree --name-only`（以及 `diff`/`status` 的默认输出）会把**非 ASCII 路径转义成八进制引号串**，
和本地 `os.walk` 拿到的原始 UTF-8 路径永远对不上；比对脚本必须用 **`-z`（NUL 分隔、不转义）并按字节处理**，
而且判「两份代码是否同一版本」要在归一化行尾之后再比哈希，否则 CRLF 会被读成内容改动。

## 触发条件与影响

- 项目或功能：判断本地未跟踪目录与远端已提交目录是否同一份，决定 `git pull` 前要不要处理它
- 环境与版本：Windows 11；git 2.52.0.windows.1；`core.autocrlf=true`；仓库内有中文目录名（`跨平台应用开发/`）
- 触发条件：脚本用文本模式的 `--name-only` 输出做集合交集
- 影响范围：会得出「56 个文件与本地 57 个文件零交集」的假结论，进而误判为「本地是另一套代码」

## 复现步骤

1. 前置条件：仓库含中文路径，且该路径在某个提交里
2. 操作或命令：
   ```bash
   git ls-tree -r --name-only <rev> -- 跨平台应用开发
   ```
3. 预期结果：每行是可直接与文件系统路径比较的 UTF-8 路径
4. 实际结果：每行是 `"\350\267\250\345\271\263...\345\217\221/.gitignore"` 这种**带引号的八进制转义串**
   → 与 `os.walk` 的 `跨平台应用开发/.gitignore` 交集为 0

## 证据

同一份数据，两种取法（本轮实测）：

```
--name-only（文本）: 只在远端 56 / 只在本地 57 / 同名且哈希相同 0     ← 假结论
ls-tree -r -z（字节）: 远端 56 本地 57 / 同名且同哈希 46 / 同名不同 10 / 只在本地 package-lock.json / 只在远端 0
10 个「不同」再按 CRLF→LF 归一化后重算 git-hash: 全部相同 → 真实内容差异 0
```

## 根因分析

- 已确认的根因：git 的 `core.quotePath` 默认 `true`，非 ASCII 路径在文本输出里被转义；`-z` 走 NUL 分隔且不转义。
- 叠加因素：`core.autocrlf=true` 时，仓库内存 LF、Windows 工作区落 CRLF，未跟踪副本与提交内容**只差行尾**，
  直接比原始哈希会把它当成改动。
- 问题归属：本次取证脚本写法（不是被测仓库的问题）。

## 最小修复

1. 取清单一律 `git ls-tree -r -z --name-only`（或 `git diff -z --name-only`、`git status --porcelain -z`），
   用 `subprocess` 的 **bytes** 接收，自己按 `b'\0'` 切分、`decode('utf-8')`。
2. 比对 blob 是否同一版本：本地字节算 `git hash-object` 同算法（`sha1(b"blob %d\0" + data)`），
   与 `ls-tree` 给的 sha 直接比；**先试 `data.replace(b'\r\n', b'\n')` 再判差异**，把「仅行尾差异」和真改动分开计数。
3. 结论要分层写：同名同哈希 / 仅 CRLF 差异 / 真实内容差异 / 单边独有，四类分开报，别只报一个「不同」。

## 验证记录

- [x] 假结论复现：`--name-only` 版交集 0
- [x] 修复版跑通：`-z` 版得 46 同哈希 + 10 仅 CRLF + 0 真差异 + 本地多 1 个 `package-lock.json`
- [x] 归一化断言：10 个文件 CRLF→LF 后哈希与远端 blob 全部相等
- [x] **同一轮内二次复发（`git diff --name-only`）**：用它算「远端新增文件 ∩ 本地未跟踪」得 **0 撞车**，
  换成 `ls-tree -r -z` 求集合差后是 **56/56 全撞** —— 差别就是中文目录名。
  ⇒ 教训：**只要比对对象含非 ASCII 路径，任何 git 文本模式输出都不可信**，一律 `-z` + bytes；
  `-z` 对 `diff --name-only` 的分隔行为与文档不符（实测整段只按换行分），所以宁可改用 `ls-tree -z` 自己求差。

## 可复用检查动作

- 写「拿 git 输出和文件系统比对」的脚本时，先问一句**路径里有没有非 ASCII**；有就一律 `-z` + bytes。
- Windows 上判两份代码是否同一版本，**未归一化行尾前不得下「有改动」结论**（`core.autocrlf=true` 是常态）。
- 一次比对结果出现「全部不匹配」这种极端值，先怀疑取数方式，再怀疑被测对象。

## 适用范围与不适用范围

- 适用：任何含中文/空格/emoji 路径的 git 仓库；跨平台行尾混杂的仓库
- 不适用：纯 ASCII 路径且 `core.quotePath=false` 时文本模式也可用（但仍不推荐依赖）

## 剩余风险

- 若远端提交里的文件本身带 BOM 或混合行尾，归一化后仍会残留差异，本条未覆盖该情形。
