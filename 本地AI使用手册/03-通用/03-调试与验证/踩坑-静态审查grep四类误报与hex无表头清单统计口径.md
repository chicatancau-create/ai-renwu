# 问题：静态审查 grep 的四类误报与编码清单统计口径

## 一句话结论

用 grep 做合规审查时，四类命中是误报而非缺陷：CSS-in-JS 的 camelCase（`aspectRatio`）躲过连字符检索、白名单行带前导 `/` 躲过 `^!` 锚定、可复用组件的自身 id 被当成「死组件」、hex 编码且无表头的 TSV 被「行数减一」少算一行。每条命中必须回源码分诊后才能写进发现。

## 触发条件与影响

- 项目或功能：对 QML/CSS/TSV 做规则符合性审查（本机 CodeWeave 修缮审查）。
- 环境与版本：Git Bash grep + Python 统计；QML 设计令牌、CSS-in-JS、hex TSV 内容包。
- 触发条件：以单一正则/单一锚定/单一行数假设下「未实现/违规/缺失」结论。
- 影响范围：审查发现文档若含误报，执行方会照错结论改代码或浪费工时。

## 复现步骤

1. 前置条件：存在 `aspectRatio: '16 / 9'`（CSS-in-JS）、`.gitignore` 的 `!/工作区/…` 白名单、`ShellDialog.qml` 内 `id: dialog`、hex 无表头 `catalog.v1.tsv`。
2. 操作：分别用 `grep 'aspect-ratio'`、`grep '^!工作区'`、「定义 id 无 `.open()` 调用即死组件」、`wc -l 减一` 统计。
3. 预期：得到「未实现 / 无白名单 / 死组件 / N-1 行」。
4. 实际：四项全部与事实相反——已实现且有测试、白名单存在、组件由自身 API 打开、真实行数 N。

## 证据

- `aspect-ratio` 全 src 0 命中，但 `markdown.tsx:55` 为 `aspectRatio: '16 / 9'`，且 `markdown.attachments.test.tsx:54` 断言 `img?.style.aspectRatio === '16 / 9'`。
- `grep -c '^!工作区' .gitignore` = 0，实际 :50-54 为 `/工作区/*` + `!/工作区/工程审查待办.md` + `!/工作区/config/` + …（前导 `/`）。
- 「无 open 调用的 Dialog」命中 `ShellDialog.qml` 的 `dialog` 与 `ShellPopup.qml` 的 `shellPopup`——二者是可复用外壳的自身 id，由组件 API 打开，非死组件。
- `catalog.v1.tsv` 按「行数减一」得 73，解码后实为 **74 行全 published**（hex 编码、无表头）；同目录 exercises/hints  likewise 各少算 1。

## 根因分析

- 已确认的根因：检索式与数据形态不匹配（命名风格、行首锚定、组件生命周期、编码与表头假设），不是代码缺陷。
- 排除过的假设：曾怀疑「图片占位未实现」「白名单缺失」「组件半接线」「内容丢失」，均被源码/解码推翻。
- 问题归属：审查方法（修改前已存在的认知陷阱）。

## 最小修复

审查流程加一条硬规则：**每条 grep 命中在写入发现前必须回源码分诊**；统计编码清单前先解码并确认有无表头；判「死组件」要看组件是否被自身 API/父级实例化，而非只看 `.open()`。

## 验证记录

- [x] 格式化或静态检查：四类误报逐一用源码/解码复核。
- [x] 类型检查或编译：不适用。
- [x] 单元、集成或端到端测试：`aspectRatio` 有现成测试断言佐证。
- [x] 构建：不适用。
- [x] 启动或手动回归：解码 catalog 得 74/4/13/74，与部署副本逐字节一致。

## 可复用规则

1. 查 CSS 属性同时查连字符与 camelCase 两种写法。
2. 查 `.gitignore` 白名单用 `grep '!.*工作区'` 而非 `^!工作区`（允许前导 `/`）。
3. 判死组件先排除「可复用外壳自身 id」。
4. 统计 TSV/CSV 前先确认编码与表头；hex 清单先 `bytes.fromhex` 解码再数行。
适用：任何以 grep/行数做合规或规模结论的审查。例外：有 schema 声明表头存在时可按声明处理。

## 适用范围与不适用范围

- 适用：静态合规审查、内容包规模核对、死代码判定。
- 不适用：运行时行为判定（仍需真实运行/截图）。

## 剩余风险

分诊依赖审查者读到正确源码位置;若源码本身漂移，需以内容搜索重新定位而非信旧行号。
