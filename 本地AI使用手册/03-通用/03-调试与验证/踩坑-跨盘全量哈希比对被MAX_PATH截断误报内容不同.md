# 问题：跨盘全量哈希比对被 MAX_PATH 截断误报「内容不同」

## 一句话结论

同一份资料的活副本与备份区做逐字节比对时，备份侧因根目录路径比活副本长 4 个字符，把 8 个处于临界长度的长文件名顶到 260 字符，普通 `open()` 直接报 `Errno 2 No such file or directory`，脚本若把「打不开」降级成「哈希为空/不同」，就会报出 8 条假的「内容不同」；加 `\\?\` 前缀重算后 8 条全部一致，真正的内容差异只有 1 个文件。

## 触发条件与影响

- 项目或功能：`G:\CodeWeave\工作区\全栈工程师学习资料库`（活副本）与 `G:\数据备份\全栈工程师学习资料库_20261120_合并版`（备份区）全量差异扫描。
- 环境与版本：Windows 11 + NTFS，Python 3（`os.walk` + `hashlib.sha256`），比对对象 37.8 万文件 / 14.72 GB；两侧根路径长度 28 字符 vs 32 字符。
- 触发条件：目标文件相对路径较长，**两侧根路径长度不同**，且长的一侧刚好越过 260 字符（含盘符与反斜杠）；同时比对脚本对 `open` 失败没有 fail-fast，而是继续产出 `sha256=None`。
- 影响范围：所有「把超长路径的读失败当成内容差异」的比对/备份校验脚本；本例会影响差异结论的正确性（8 假阳性 vs 1 真差异，结论从「9 处不同」变「1 处不同」）。同步、去重、迁移校验、镜像一致性检查都属同类风险。

## 复现步骤

1. 前置条件：准备两侧路径长度不同的同一批文件，其中至少一个文件路径在长的一侧达到 260 字符（例如 `05-外部资料库/**` 下用整条 URL 命名的文件）。
2. 操作或命令：
   ```python
   import hashlib
   def sha(p):
       h = hashlib.sha256()
       with open(p, "rb") as f:      # p 长度 == 260 时这里就炸
           for b in iter(lambda: f.read(1 << 20), b""):
               h.update(b)
       return h.hexdigest()
   ```
3. 预期结果：两侧同名文件哈希相同。
4. 实际结果：长路径侧抛 `FileNotFoundError: [Errno 2] No such file or directory: 'G:\\数据备份\\...\\<超长URL文件名>'`；若脚本用 `except Exception: return None` 包住，则该条目被算成「内容不同」，差异报告多出 8 条假阳性。

## 证据

- 普通 `open()`：live 侧 ERR=0，backup 侧 ERR=8（全部是备份侧），无两侧同时 ERR 的条目 —— 说明不是文件缺失，而是路径长度问题。
- 改用 `"\\\\?\\" + abspath` 重算同样 8 个文件：8/8 与活副本 SHA-256 完全一致。
- 对备份侧 max path 探针记录到失败项长度恰为 260 字符；备份根路径 `G:\数据备份\全栈工程师学习资料库_20261120_合并版`（32 字符）比活副本 `G:\CodeWeave\工作区\全栈工程师学习资料库`（28 字符）长 4 字符，正好把同一批文件名顶过界。
- 修正后最终结论：同路径 378,124 条全部逐字节一致；真正内容差异仅 `CodeWeave/content-manifest.json` 1 条（6,453 B vs 7,637 B）。

## 根因分析

- 已确认的根因：Win32 传统 `CreateFileW` 路径上限 `MAX_PATH = 260`（含盘符、反斜杠与结尾 NUL 前的全部字符）。`\\?\` 长路径前缀会跳过规范化与长度检查，普通 API 不会。两侧根路径长度差 4 字符，使同一相对路径在一侧合法、另一侧越界 —— 所以「文件明明存在却读不到」。
- 排除过的假设：① 备份缺文件 —— 用 `os.path.exists`/目录清单比对已证明文件条目存在；② 权限/ACL —— 同盘其他文件全部可读，只有临界长度项失败；③ 磁盘或杀软拦截 —— 加前缀后 100% 可读，未改任何安全设置；④ 编码问题 —— 失败项与成功项文件名同为中文+ASCII 混合，不呈编码规律。
- 问题归属：环境或依赖（Windows 路径长度限制 + 两侧根路径长度不同），非扫描脚本逻辑 bug，但脚本「读失败降级为差异」的容错策略放大了误报。

## 最小修复

- 读取函数统一加长路径前缀，且只在需要时加，避免影响普通路径的语义：
  ```python
  def long(p):
      p = os.path.abspath(p)
      return p if p.startswith("\\\\?\\") else "\\\\?\\" + p
  ```
- 比对脚本改为 **fail-fast**：读失败必须记入独立 `error.tsv` 并让整轮退出码非 0，绝不允许「读不到 → 哈希为空 → 记为内容不同」。差异报告里「内容不同」「读失败」「一侧缺失」必须是三个互斥分类。
- 相对路径键不要用 `\\?\` 前缀形态（它会破坏大小写不敏感、`/` 归一化等处理），前缀只在最终 `open` 那一刻加。

## 可复用规则

1. **跨盘/跨目录做哈希比对前，先比两侧根路径长度**。只要有一侧根路径更长，就必须假设长文件名会越界，直接全程用 `\\?\` 前缀读（或全程用 `\\?\` + `os.scandir` 遍历），不要等报错再补。
2. **「读失败」永远不许等于「内容不同」**。读失败必须单独落 `error.tsv` 并让本轮结果标记为不可信；出现非零错误数时先修工具再下结论。
3. 差异分类至少三分：`仅一侧有` / `内容不同` / `读失败`，三者互斥且计数可加总。
4. 判定「备份是否完整」时，文件数、目录数、总字节数、逐文件哈希四件事都要对；只用文件数和大小会漏掉同大小不同内容的篡改。
5. Git 侧等价性另验：`rev-parse HEAD`、`cat-file -p HEAD^{tree}`、`ls-files | wc -l`、`fsck`、`count-objects` 五项同值，才敢说「Git 层面一致」；单看提交号不够。

## 适用范围与不适用范围

- 适用：Windows + NTFS 上的跨目录/跨盘全量比对、备份校验、迁移前后一致性验证、镜像同步审计；任何两侧根路径长度不同的场合同样适用。
- 不适用：Linux/macOS（无 MAX_PATH 限制，但有 255 字节单段限制）；已启用长路径策略（`LongPathsEnabled=1` 且目标程序 manifest 声明）的情况虽不必然触发，但脚本仍建议统一加前缀以免环境差异。

## 剩余风险

- 更深的单段路径（>255 字符）加前缀也无解，需靠缩短目录层级；本例未遇到。
- 加 `\\?\` 前缀后相对路径与 `.`/`..` 不再被规范化，脚本若混用两种形态可能对不上键；需保证「遍历/键」用普通路径、「打开」才用前缀形态。
- 本次结论只覆盖扫描时刻（2026-11-25）；任何一侧后续写入都会产生新差异。
