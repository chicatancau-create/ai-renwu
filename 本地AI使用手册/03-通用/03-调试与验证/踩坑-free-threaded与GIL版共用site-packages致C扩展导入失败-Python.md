# 问题：双击启动的 GUI 程序只出一行红字，`_imaging` 导入失败

## 一句话结论

`python3.14t.exe`（free-threaded / 无 GIL 构建）与 `python3.14.exe` **共用同一份 site-packages**，
但 Pillow 的 C 扩展 `_imaging.pyd` 是按 GIL ABI 编译的 —— free-threaded 解释器加载不了它。
而 `.pyw` 双击会经 `C:\Windows\pyw.exe`（Python 启动器），**它默认挑 3.14t**，于是程序必挂。

## 触发条件与影响

- 项目或功能：Python + tkinter + Pillow 的桌面 GUI（本例：`cc-hud` 悬浮面板）
- 环境与版本：Windows；`D:\PyCharm\Python\` 下同时存在 `python.exe`(3.14.2) 与 `python3.14t.exe`(3.14.2, free-threaded)；Pillow 12.3.0
- 触发条件：用 `.pyw` 双击启动，或启动脚本里写**裸 `pythonw`**
- 影响范围：程序完全不工作，但**没有任何控制台输出**（`pythonw` 无 stderr），只表现为"没启动"

## 复现步骤

1. 前置条件：同一目录下同时安装 GIL 版与 free-threaded 版 Python，Pillow 装在共享的 site-packages
2. 操作：
   ```bat
   D:\PyCharm\Python\python.exe   -c "from PIL import Image; print('ok')"
   D:\PyCharm\Python\python3.14t.exe -c "from PIL import Image; print('ok')"
   ```
3. 预期结果：两个都输出 ok
4. 实际结果：前者 ok；后者
   ```
   ImportError: cannot import name '_imaging' from 'PIL' (…\site-packages\PIL\__init__.py)
   ```

## 证据

两个解释器、同一份 site-packages：

| 解释器 | `sys._is_gil_enabled()` | Pillow 12.3.0 | 结果 |
|---|---|---|---|
| `python.exe`（GIL） | True | 同一路径 | **正常** |
| `python3.14t.exe`（free-threaded） | False | 同一路径 | **`_imaging` 导入失败** |

故障现场（GUI 面板里只剩一行红字，截图为证）：

```
cannot import name '_imaging' from 'PIL._typing'
```

`.pyw` 关联链：

```
.pyw  ->  Python.NoConFile  ->  "C:\Windows\pyw.exe" "%L" %*
pyw.exe 默认选中的解释器  ->  D:\PyCharm\Python\pythonw3.14t.exe   ← 踩坑点
```

另有一处同类坑：**PATH 里的 `pythonw` 不一定是你要的那个**。
本机工具环境的 PATH 里 `pythonw` 指向一个托管构建的 3.13.12，**该构建没有 tkinter** ——
`start-hud.bat` 原来写裸 `pythonw`，同样是"点了没反应"。

## 根因分析

- 已确认的根因：
  1. free-threaded 与 GIL 版 Python **共享 `Lib\site-packages`**；
  2. 带 C 扩展的包（Pillow、numpy…）编译时绑定 ABI tag（`cp314` vs `cp314t`），
     `.pyd` 不能跨构建加载；
  3. `.pyw` 的文件关联交给 `pyw.exe` 决定解释器版本，**不受项目控制**。
- 排除过的假设：
  - 以为是 Pillow 没装（`import PIL` 能过，`__version__` 也正常 —— 只是 `_imaging` 加载失败）；
  - 以为是代码 bug（同一份代码用 GIL 版解释器跑完全正常）。
- 问题归属：环境或依赖

## 最小修复

1. **启动器里把解释器钉死**，不要写裸 `pythonw`、也不要依赖 `.pyw` 关联：
   ```bat
   set "PYW=D:\PyCharm\Python\pythonw.exe"
   if not exist "%PYW%" (echo [x] 找不到解释器：%PYW% & pause & exit /b 1)
   "%PYW%" -c "import tkinter, PIL.Image" 2>nul
   if errorlevel 1 (echo [x] %PYW% 缺少 tkinter 或 Pillow & pause & exit /b 1)
   start "" "%PYW%" "%~dp0app.pyw"
   ```
2. **启动前做一次依赖自检**：`pythonw` 没有 stderr，静默失败是最难查的故障形态。
3. 若必须兼容"用户双击 `.pyw`"：在入口处检测并自我重启到正确解释器（判断 `sys._is_gil_enabled()`
   或 try-import Pillow，失败则 `Popen` 正确的 `pythonw` 后 `os._exit(0)`）。

## 可复用规则

- 看到 `cannot import name '_xxx' from 'PIL'` / `ImportError: DLL load failed` 这类
  **"包在、但 C 扩展加载不了"** 的报错，第一反应是**解释器构建与 ABI 不匹配**，不是包没装。
- 判断当前跑的是哪个构建：`python -c "import sys; print(sys.version, sys._is_gil_enabled())"`。
- 给 GUI/后台程序写启动器时，**永远显式写解释器绝对路径**，并加一行 import 自检。
- `.pyw` / `.py` 的文件关联属于"用户环境"，**不能当启动契约**。

## 适用范围与不适用范围

- 适用：Windows 上任何"双击启动的 Python GUI"；多版本 Python 共存；带 C 扩展的第三方包
- 不适用：纯标准库脚本（不受 ABI 影响）；通过打包工具（PyInstaller 等）分发的程序

## 剩余风险

- 硬编码解释器路径在用户换 Python 安装位置后会失效 —— 所以自检要给出**可读的失败提示**，
  而不是静默退出。
- 若将来 Pillow 发布 `cp314t` 轮子，该问题自然消失，但**其他 C 扩展仍可能踩同一个坑**。
