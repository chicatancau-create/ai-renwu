# 问题：CC Switch 路由队列里两个供应商都标「熔断」，看起来像双双宕了

## 一句话结论

熔断标只是**断路器记住的历史失败**，不等于现在坏；而这两次的历史失败一个是 **Cloudflare 按客户端指纹封非浏览器 HTTP 客户端**（`403 / error code: 1010`），一个是**拿错模型名去问不提供该模型的分组**（`503 model_not_found`）——都不是线路故障。判线路必须**带浏览器 UA、用该供应商配置里的真实模型名**打最小请求，否则探针自己就会造出一个假故障。

## 触发条件与影响

- 项目或功能：CC Switch v4.x 的 Claude Code 路由（按队列 / 自动故障转移）
- 环境：本机 `~/.cc-switch/cc-switch.db`（SQLite）；`proxy_config` 里 claude 档阈值 = 连续失败 8 次跳闸、连续成功 3 次复位、冷却 90 s、错误率 0.7、最小样本 15
- 触发条件：队列里两个供应商 `provider_health.is_healthy=0`、`consecutive_failures=9`（都越过阈值）
- 影响：看着像「两条线路全废」，实际全可用；误判会导致白改配置、白换供应商

## 证据（本轮实测）

库里的历史失败原文：

```
OpenOx Claude  最后失败 11-01 05:41:39  上游错误 (状态码 403): "error code: 1010"
aruhub         最后失败 11-01 05:41:41  上游错误 (状态码 503): model_not_found
                                        No available channel for model deepseek-v4.1-flash
                                        under group Claude-Kiro-A 特价 (distributor)
```

同一时刻用浏览器 UA + 各家配置里的模型名重打 `/v1/messages`（`max_tokens=4`）：

```
OpenOx  claude-opus-5-5     -> HTTP 200
aruhub  claude-sonnet-5-5   -> HTTP 200
aruhub  claude-opus-5-5     -> HTTP 200
aruhub  claude-fable-5-1    -> HTTP 200
```

对照组（证明探针本身会造故障）：

```
OpenOx  用默认模型名 claude-sonnet-4-5 -> HTTP 400 "model not allowed for this api key"
aruhub  用默认模型名 claude-sonnet-4-5 -> HTTP 503 model_not_found（同历史错误）
直连 / 走本机 7897 代理 结果一致 → 与出口无关
```

## 根因分析

- **`403 error code: 1010`**：Cloudflare 的「按浏览器签名封禁」。挂在 CF 后面的中转站会拒绝**非浏览器 HTTP 客户端**的指纹；程序化探针若不带浏览器 UA 就会被 1010 拒，而同一时刻人用浏览器访问是好的。⇒ 熔断计数被客户端形态污染。
- **`503 model_not_found`**：new-api 型中转按「分组」供模型，分组里没有该模型的可用渠道就回这个。**用错模型名**（这里是拿 `deepseek-v4.1-flash` / `claude-sonnet-4-5` 去问只供 `*-5-5` 的分组）会稳定复现，与站点健康无关。
- 排除过的假设：站点宕了（200 反证）；密钥失效（400 的文案是「model not allowed for this api key」，说明 key 已被认出）；出口网络（直连与走代理同结果）。
- 问题归属：**探针写法 + 请求侧模型名**，不是被测服务。

## 最小修复 / 正确判法

1. 判线路只看**最小补全请求**，且请求头带真实浏览器 `User-Agent`（否则 CF 会给你 1010 假死）。
2. 模型名**从该供应商自己的配置里取**（本机在 `providers.settings_config` 的 `env.ANTHROPIC_DEFAULT_*_MODEL`），不要拿通用默认名试。
3. 结论分层报：`200 可用` / `400 该 key 不供此模型` / `503 分组无此模型渠道` / `403 1010 客户端指纹被 CDN 拒` / `401/403 鉴权或额度` —— 这五种成因和处置完全不同，别合并成「线路不通」。
4. 熔断状态复位：靠**真实流量连续成功**（本机阈值 3 次）或界面里的重置项；**不要直接 UPDATE 应用正在打开的 SQLite**（会撞锁 / 写坏）。

## 可复用规则

- **任何「健康状态/熔断/降级」标都只是历史计数**。要判当下，重新打一次最小请求；要判成因，读它存的 `last_error` 原文。
- 用程序探针测第三方 HTTP 服务前，先假定**探针自己可能是失败原因**：UA、TLS 指纹、模型名、协议路径（`/v1/messages` vs `/v1/chat/completions`）任一项不匹配都会造出假故障。

## 适用范围与不适用范围

- 适用：CC Switch / 自建网关 / new-api 型中转 + Cloudflare 前置的第三方 API
- 不适用：真·连接层故障（DNS 解析失败、TCP 超时、TLS 握手断）——那些在日志里是 `ERR` 而不是带状态码的上游错误

## 剩余风险

- CF 的 1010 规则可能随时间变化，本轮「浏览器 UA 能过」不代表长期能过；下次复现要重测。
- 熔断复位依赖真实流量，若长时间没有请求，红标会一直挂着（本例就是 11-01 跳闸、11-03 仍显示）。
