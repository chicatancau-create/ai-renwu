# 问题：浮层提示不自动消散，会被用户当成删不掉的悬浮元素

> 2026-11-15 回写（当时修复未实施）。**2026-11-16 修复并验证，升级 verified**，见「最小修复」与「验证记录」。

## 一句话结论

`position: fixed` 的成功类提示条若只靠点击清除、没有自动消散，会在面板上挂几天，被用户当成「要求隐藏却还在显现」的悬浮垃圾；用户不会把它理解为一次性通知。

## 触发条件与影响

- 项目或功能：cc-hud 主面板（G:\cc-hud\web\src\App.tsx 的 `notice` → `.toast`）。
- 环境与版本：React 18 + WebView2；`.toast { position: fixed; right:16px; bottom:16px; }`。
- 触发条件：任一次导出/命令成功写入 `setNotice(...)` 后，无定时器清除，仅 `onClick` 清除。
- 影响范围：提示条长期盖在内容上；用户两次截图要求「隐藏这个位置的东西」，并一度怀疑是删不掉的悬浮状态图标。

## 复现步骤

1. 前置条件：面板处于洞察布局，曾触发一次导出。
2. 操作或命令：不点击提示条，放置任意长时间后截图。
3. 预期结果：通知短暂出现后消失。
4. 实际结果：2026-11-13 10:51 的截图里仍挂着「已导出 G:\cc-hud\cc-hud-usage-all.json（345944 B，rev 3）」，与 11-11 导出那次同一条。

## 证据

- 代码事实：`App.tsx` 中 `notice` 只有 `setNotice(...)` 写入与 `onClick={() => setNotice("")}`，全文件无 `setTimeout` 清除 notice 的逻辑（grep 核实）。
- 截图像素定位：亮文字行集中在 y≈1231–1239（面板右下角），裁图目视确认即该提示条。
- 用户原话：「把画红前面位置东西隐藏吗，隐藏了，不要让他显现，实在不行的话，还是隐藏吧」。

## 根因分析

- 已确认的根因：toast 生命周期设计缺失（无 auto-dismiss），不是渲染 bug、不是第二窗口。
- 排除过的假设：不是桌面圆点窗口（`dot_created:false`、进程树只有一个 WebView2 主窗口）；不是外部程序图标（提示条文字与导出回包字段逐字对应）。
- 问题归属：修改前已有。

## 最小修复

**2026-11-16 已实施**（G:\cc-hud\web\src\App.tsx / app.css）：
1. `notice` 改为 `{text, tone}`；**导出成功不再写 notice**（按钮与菜单两条路径都只 `setExportResult`，留痕在诊断页「导出」行）。
2. 其余 notice 自动消散：`useEffect` 里 `setTimeout`，info 4000ms / error 8000ms，notice 变化时清旧定时器；点击仍可立即关闭。
3. `.toast[data-tone="error"]` 用错误色边框/文字，成功与失败不靠颜色单一区分（另有文字语义）。
4. 错误提示保留（项目硬要求）：设置失败/导出失败/命令失败/电源失败仍会显示，只是不再常驻。

## 可复用规则

- 任何 `position: fixed/sticky` 的提示浮层必须有自动消散或显式关闭，且成功类默认短时（≤5s）。
- 验收截图要覆盖「操作后 N 秒」的状态，不能只截操作瞬间；否则「常驻浮层」这类缺陷永远漏检。
- 用户说「隐藏某个位置的悬浮东西」时，先按 DOM/像素确认归属，再决定是删窗口还是改生命周期——两者修法完全不同。

## 适用范围与不适用范围

- 适用：桌面壳应用（WebView2/Electron/Tauri）与网页的 toast/notice 设计。
- 不适用：模态确认框（电源操作等危险动作的确认必须停留等用户决策）。

## 剩余风险

- 自动消散时长若太短，慢读者会漏看导出路径；需与「诊断页留痕」配套。
