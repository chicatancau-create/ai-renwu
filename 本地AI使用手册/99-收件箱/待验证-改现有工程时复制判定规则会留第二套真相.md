# 问题：新视图缺「来源」信息，抄一份分类规则还是把来源传下去

> `needs-review` 表示尚未完成验证；只有复现、定位、修复和验证都完成后，才改为 `verified`。

## 一句话结论

待确认。倾向结论：工程里已有按身份字段分类的核心分类器时，**不要**在视图层复制一份判定；把分类所需的输入（本次是「来源」）沿调用方显式传下去，视图模型只补运行时本来就存在的字段。

## 触发条件与影响

- 项目或功能：给一个大仓的多个 UI 套件加同一份视觉规则。
- 环境与版本：TypeScript + React，多 suite 目录，边界规则由测试锁住。
- 触发条件：某个套件的数据模型比核心分类器少了必要输入（分类器签名要 `source`，模型里没有）。
- 影响范围：抄规则＝两处真相，日后一边改一边不改，视觉/行为不一致且难定位。

## 复现步骤

1. 前置条件：核心分类器注释里已明写「X 套件目前不用它」。
2. 操作或命令：在 X 套件里重写等价判断（最快），与改为传 `source` + 复用分类器（本次做法）。
3. 预期结果：两种都能跑。
4. 实际结果：两种都能跑——所以差别不在功能，而在后续维护；本条因此还不能算已验证的优势。

## 证据

- 本次「传 source」路线通过了 `tsc --noEmit` 与两个边界测试文件（20 项全绿），共享视觉组件落在 `src/components/` 而非任一 suite 内，因为边界规则明确禁止 suite 互 import。
- 尚无第二例，无法证明它比抄规则真的更好。

## 最小修复

遇到「分类器缺输入」时，先找那个输入在调用方是否已知（本次三个消费方各自都知道自己是哪个来源），已知就传；只有跨层拿不到才考虑在核心加一个不依赖来源的窄判定，并在注释里写清它和原分类器的关系。

## 可复用规则

待第二例后成文。当前只能作为检查动作：改大仓前先搜「这个判断有没有现成的分类函数」，有就看它缺什么输入、输入在调用方能不能拿到，**不要**在调用方复制它的逻辑。

## 适用范围与不适用范围

- 适用：有多套件/多视图共享语义的成熟工程。
- 不适用：一次性脚本、原型；以及分类器本身设计得不可复用（需要重构签名）的场景。

## 剩余风险

把 source 沿三层调用方传下去会污染中间组件的 props 面；本次只有三个来源，规模更大时可能需要换成 context 而非 props——未验证。
