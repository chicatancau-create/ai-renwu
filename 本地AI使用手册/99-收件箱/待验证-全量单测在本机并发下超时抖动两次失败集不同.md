# 问题：同一份代码两次全量跑，失败数从 4 变 12、失败文件集也不同

> `needs-review` 表示尚未完成验证；只有复现、定位、修复和验证都完成后，才改为 `verified`。

## 一句话结论

「全量跑挂了 N 项」这句话在并发负载下**没有归因价值**：同一代码两次运行的失败集会自己变。要判是不是自己改坏的，做的是**对照实验**——把改动挪开跑同一批文件，再恢复改动跑同一批文件，两边都绿才叫与本次改动无关。

## 触发条件与影响

- 项目或功能：几百个测试文件、含网络 mock 与 IndexedDB/存储 mock 的前端工程，用 vitest 全量跑。
- 环境与版本：Windows 11、Node 24、vitest 4.x；同一台机器上还开着 dev server + Electron 应用在放音乐。
- 触发条件：`npm run test` 全量跑，看到红字。
- 影响范围：要么误报「我改坏了」去回滚正确改动，要么反过来把真问题当成抖动放行。

## 复现步骤

1. 前置条件：工作区有未提交的改动，另有应用在跑占 CPU。
2. 操作或命令：连跑两次 `npm run test`。
3. 预期结果：同一代码基线，两次失败集相同。
4. 实际结果：第一次 `Tests 4 failed | 7115 passed`，第二次 `Tests 12 failed | 7107 passed`，失败文件集不同（qqTransport / kugouTransport / neteaseDailyRecommendations / neteaseReplacement / themeSyncRegistry / qqQrDiagnostics，全是网络 mock 与 IndexedDB 类），报错形式是 `Test timed out in 5000ms`。

## 证据

对照实验（都是只跑同一批 3 个文件）：

| 状态 | 结果 |
| --- | --- |
| 改动挪回干净树 | `3 passed (3)` / `68 passed (68)` |
| 恢复改动后 | `3 passed (3)` / `68 passed (68)` |

挪动前后对每个受影响文件做 `cmp` 逐字节校验，7 个文件全部一致，排除「挪丢了」。

## 根因分析

- 已确认的根因（现象层）：这些用例默认 5s 超时，全量并发时 `transform` 累计耗时近千秒量级，机器被 dev server + Electron + 测试 worker 同时占住，个位秒的超时预算先崩。**未确认**具体是哪一类资源饥饿（CPU 调度 vs IO），本轮没测。

## 最小修复

不改被测代码，改**判定流程**：

1. 拿到全量失败清单后，第一动作是原样再跑一次——失败集变了就证明是抖动，不要立刻归因。
2. 归因用单文件级对照：`npx vitest run -c vitest.config.ts <失败文件…>`，分别在「改动挪开」和「改动恢复」两种状态下跑。
3. 挪动前先 `git status --porcelain` 列清单并整份备份，恢复后用 `cmp` 逐文件校验一致。

## 可复用规则

1. 报「测试挂了」必须附「挂了几个 + 两次跑是否一致」；只有不一致证据时结论写「抖动，未归因」。
2. 归因的最小可信动作是**单跑同一批文件的对照**，不是全量重跑。
3. 适用：本机资源紧张时跑大套件。不适用：CI 上稳定复现的同一失败集（那种要先怀疑代码）。

## 适用范围与不适用范围

- 适用：vitest/jest 这类带默认短超时、依赖 fake timers/网络 mock 的套件。
- 不适用：确定性断言失败（比较值不等），那种与负载无关。

## 剩余风险

未定位饥饿的具体资源；未测把 `testTimeout` 调大能否稳定消除；单次任务的经验，**跨项目通用性待第二例**，故状态保持 `needs-review`。
